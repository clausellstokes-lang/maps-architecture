### 2.2 Voronoi Graph — 2017-03-30 — https://azgaar.wordpress.com/2017/03/30/voronoi-graph/ — Graph
- **Method / rationale [STATED].** A map is recognisable by its land/water partition, so a heightmap is needed first. Three ways: noise, graph, or both; pure noise terrains "look a bit artificial", so a graph is "the better way for a maps tending to have plausible look". Follows Amit Patel's polygonal map tutorial; square/hex graphs "look fine" but "really good result could be achieved only with relaxed Voronoi diagram". Uses d3-voronoi (Fortune's algorithm). Random sites tessellate irregularly; one Lloyd relaxation (re-seed at centroids) fixes most of it; a second pass "takes some time with kilos of points, but improvement is not so significant" and the difference "won't be obvious in close-to-real generation". Per polygon the generator needs the site, the edge coordinates and neighbour references; neighbours are recovered by walking each cell's half-edges and taking the index of the cell on the other side. Voronoi polygons vs Delaunay triangles: "the best variant is to use both of them", but the generator "works with Voronoi polygons only".
- **Later-added paragraph [STATED; INFERRED to be a post-publication edit].** "After some time, introducing a new feature, I realized the 1 iteration is not enough for a things like path-finding or a polygon-based drawing. Produced grid is too irregular and we need up to 20 Lloyd's iterations". Solution: start from a regular-by-construction point set — Poisson-disc sampling (Jason Davies' algorithm, Mike Bostock's D3 implementation) "without any relaxation".
- **Parameters [STATED].** Demo sizes 100 and 1000 sites; Spectral sequential colour scale from d3-scale-chromatic for colouring.
- **Limitations [STATED].** "I'm not a D3 expert and my code contains redundant lines and errors"; understands Voronoi theory "only in basics".
- **Comments.** Five pingbacks only (own later posts; a 2022 third-party tutorial).
- **Earlier note.** Agreed on random sites + one Lloyd pass [SHOWN-code] → [STATED]; the comment "more iterations didn't get much better result" is now the author's prose. **Corrected**: the move to Poisson-disc is *stated* in this post and already in use in the author's fiddles by 2017-06-17 (§2.7), earlier than the gist's October 2017 revision. ### 2.3 Heightmap — 2017-04-01 — https://azgaar.wordpress.com/2017/04/01/heightmap/ — Shape
- **Method / rationale [STATED].** "The easier heightmap generation algorithm I use the better result I get." Noise was not tried ("not a priority"). Algorithm: choose a random polygon, assign a height in 0–1, give neighbours the height times a decrement, continue breadth-first through unused neighbours while the height is significant; the result is a "blob" (island). The decrement ("radius") is a constant below 1 per blob and "actually controls the blob radius"; the loop ends when the current height falls to 0.01 (it never reaches zero because of multiplication); heights are capped at 1. Pure blobs are smooth, but real big islands (Ireland, Iceland are his examples) have one sharp, inlet-rich side and one straight side, which is "interesting with all of its inlets, peninsulas and harbors". Fix: before assigning, multiply by a random modifier derived from a "sharpness" setting, slightly below or above 1; values above 1 let height *increase* locally, which "provides a lot of form irregularity and allows small accompanying isles generation". Sharpness alone is not enough: the next ring must be computed from the *parent polygon's* height rather than the ring's running height, so that ridges and valleys "sprawl" from the centre. Overlap problem: with parent-based heights, overlapping blobs push the sum off scale, so on overlap the height is redefined rather than added, which in turn means later blobs cannot change the shape; his solution is one big sharp blob (parent-based variant) followed by a number of smaller, lower, smooth blobs (ring-based variant) that "cover" the big one and reshape the landform. "For my generator I create one big blob as a first step and then add 10 small blobs."
- **Parameters [STATED].** Modifier example range 0.9–1.1 (the snippet shows the modifier drawn uniformly from [1.1 − sharpness, 1.1], with sharpness 0 forcing 1 [SHOWN]); stop at 0.01; 8000 polygons "just because this amount still runs smoothly in my browser with the already added details"; a 100k-polygon experiment "with rather interesting look" needs more testing; map look "depend[s] on the graph size".
- **Limitations [STATED].** Blobs overlap badly; "I'm not a specialist in coastal geomorphology".
- **Plans [STATED].** Try noise later.
- **Comments.** Pingbacks from his later posts; a 2018-08-12 third-party pingback (Ashatej Software) says it borrowed code from this post.
- **Earlier note.** Agreed on the BFS blob, decay and sharpness range [SHOWN-code] → [STATED]. The specific peak heights (island 0.8–1.0, hills 0.1–0.5) and decrements (0.9 island / 0.99 hills) are not in the post (inputs are user-defined in the fiddle); they remain [SHOWN-code, gist 581c717]. "Third parties summarise this as particle deposition" is dropped as unnecessary.

### 2.4 Coastline — 2017-04-03 — https://azgaar.wordpress.com/2017/04/03/coastline/ — Shape
- **Method / rationale [STATED].** Simplest land/water separation: make the SVG background the water and draw only polygons at or above a threshold. "It's a good idea to have a small margin for a water height, it will be useful later." Sea level fixed at **0.2** because the Spectral scheme "already provides rather plausible colors" and "green color starts here"; the result is "close to the some of these NASA relief maps". Coastline v1: for each land polygon, every edge whose opposite polygon is water — enough to outline, but "just a set of randomly connected edges", unusable for interpolation, clip paths or fills. Features by **flood fill**: start at the polygon nearest the top-left corner, assume it is ocean (border polygons are oceanic on an island map; if the start is land, the ocean is mislabelled a lake — "a rare and non-critical issue"), flood through water neighbours and mark Ocean; then repeatedly take the first unmarked polygon: below 0.2 → Lake, else → Island, flood through same-type neighbours, assign a running number and a random adjective as a placeholder name. Coastline v2: collect edges with their type (island-ocean or land-lake) and feature number; for each feature, start with one edge, repeatedly find the edge sharing the current endpoint, append its far point, until the ring closes (the loop is capped at 2000 steps "to avoid eternal loop"); lakes get a different stroke style from sea coasts. With closed rings the coast can be filled, patterned, or smoothed with D3 curve interpolation; but a smoothed line no longer matches the polygon edges. Options weighed: (1) stop drawing individual polygons and use fills/patterns — "will save a lot of resources and I will definitely do it, but this is completely another story of moving to a hand-drawn map style"; (2) use the curved coastline as a clip path over the polygons with a background layer coloured as the lowest island polygon — "extremely slow in Chrome and just slow in Firefox", still slow when clipping only coastal polygons; (3) omit coastal polygons — fastest but polygon contours show; blurring the edge (0.5 px, 1.5 px) "not sure I like the result, especially on zooming"; hatching along the coast — "I like the hatching and definitely will use it"; (4) interpolate the polygons themselves to follow the coast — "looks no so neat as I want". Key objection to curves: "using curves as a coastlines brakes our grid structure. In my map generator I create cities and river estuaries on the coastline edges and I don't want to adjust the element to the cur[v]e any time I need to place something on the seashore." Final solution "after two days of testing": invert the problem with an **SVG mask** — a white full-map rectangle plus the coastline paths filled black inside a mask, then a water-coloured rectangle with that mask placed on a layer above the landmass, so the water "perforated mask" hides polygon parts outside the curved coast.
- **Limitations / wishes [STATED].** "I'm still not satisfied with current 'flat' style"; most interested in semi-3D effects (shading, hatching).
- **Comments.** Thomas (2017-04-13) asks why mountains are always central and there are no coastal cliffs; Azgaar (2017-04-18): "It generates a kind of volcanic islands with the highest point in the middle. ### 2.5 River systems — 2017-05-08 — https://azgaar.wordpress.com/2017/05/08/river-systems/ — Rivers
- **Precipitation [STATED].** "We do not need to fabricate rivers out of nothing and will calculate river systems based on precipitation drainage." Uniform precipitation would be "enough to create plausible rivers", but a model is "useful not only for rivers calculation, but also for biomes and erosion modeling". Scott Turner's wind model is "a bit over-complicated for a landscapes created via blobs approach and requires more detailed map". His simpler model: pick a narrow band of sites along the map border on the windward side (left border for westerlies) as "clouds"; move each cloud toward the opposite border with a random sideways walk; over land it drops some of its precipitation; meeting mountains it "disappear[s] giving away all moisture" (orographic lift, rain shadow on the lee); stop when the cloud is empty or reaches the far border; for several prevailing winds, divide the initial precipitation by the wind count and repeat per wind. The map is rough but marks humid and arid zones; smooth by averaging each cell with its neighbours.
- **Depressions [STATED].** Each cell needs a lowest neighbour; cells lower than all neighbours are depressions. Simplest fill "I can imagine": loop the land cells, lift each depressed cell slightly above its lowest neighbour (+0.01 in the snippet [SHOWN]), sort land by height descending, repeat until no depression remains. "Does it effective? No. Does it work? Yes."
- **Flux and river ids [STATED].** Process cells highest-first; each pours its accumulated water into its lowest neighbour; when a cell's flux exceeds a threshold ("e.g. 3") it is a river cell — without a threshold "all the map will be covered by rivers and this looks messy". River records hold cell, coordinates, river id and a type (source for the first cell, course after). Two per-cell outputs: precipitation (initial moisture, kept for biomes) and flux (collected water, for drawing). When water pours into a cell that already has a river, the existing id is overwritten only if the incoming river is longer, "so we can separately track both the main stream and the tributaries". Pouring into ocean/lake: if there are two or more possible pour cells and the flux is "rather big", generate a **delta** (one branch per pour cell); otherwise mark an **estuary**. "Maybe they look not very good in my implementation, but… I like it." (The snippet's delta condition reads as flux of about 30 with more than one pour cell [SHOWN; archive text garbled].)
- **Rendering [STATED].** Catmull-Rom curves through river points, drawn twice (a shade layer and the river). Weak points: not meandering; constant width. **Meanders**: insert two intermediate points per segment with a significant deviation from the straight line, the first shifted one way and the second the other way by the same amount; "looks like sine wave, but not so regular and hence more plausible". **Width**: SVG strokes cannot vary width, so split the interpolated path into small segments (path data read back through a polyfill) and stroke each with its own width. Flux as width "is looking weird"; real river width "depends on flow non-directly". Candidates: square root of flux (Amit Patel), flux and slope (Scott Turner), or **length only** (his). Why length: "It's easy and it guarantees that width will increase smoothly, which is critical in case of interactive scalable map. We cannot allow rivers to change width drastically as they will be looking ugly on a big scales"; finer segmentation "requires more resources and map will lag on dragging". (Post-hoc update line: rendering later changed to polygonal rivers.)
- **Plans [STATED].** Next post: map styling (did not happen in that order).
- **Comments.** GAZ082 (2018-01-25): why fill depressions — aren't they lakes? Azgaar (2018-01-25): "depressions should normally produce lakes. But they also tend to collect all the flux around and it looks weird. Maybe I can collect these depressed points and use them to place normal lakes after a main river routing." ### 2.6 Confluences — 2017-05-27 — https://azgaar.wordpress.com/2017/05/27/confluences/ — Rivers
- **Method / rationale [STATED].** Length-only width is "rather elegant, but tributaries don't increase the main stem volume"; real tributaries mostly don't either, "but from a world-building perspective my implementation looks a bit boring". Because meander points no longer coincide with cells (about three river elements per polygon), per-element flux would need interpolation; instead combine the two: width grows steadily with length along a stream and is recomputed from the cell's flux at a confluence. Confluences are detected in the flux function (a cell with an existing river receiving more flux) and stored; at render time an element ending at a confluence gets flux-based width. The jump was still too abrupt on zoom, so the flux value is reduced "by using root function". To make the junction smooth, the thinner (upstream) element's endpoint is shifted by half the width difference, perpendicular to the main stem: the direction comes from the angle between the confluence and the last control point of the already-rendered element (two points define the vector; the next element does not exist yet), giving a left and a right candidate point. Which side: identify whether the tributary is a left-bank or right-bank tributary using a bisector from the midpoint of the two rivers' source points to the confluence and the sign of a cross-product; right-bank tributaries shift right. Tributaries must use the main stem's angle, so main stems must render first: each river gets an Order number that is increased, when a river flows into another, by the tributary's length (incrementing by 1 "caused the situation when main flow was rendered after its tributary"); rivers render in descending Order, with a fallback to the tributary's own angle if the main stem's is still undefined. Finally, the tributary's last Bézier segment is relaxed by replacing its second control point with the midpoint between the two control points so the junction looks natural "meanwhile, it doesn't mean we start control all over the river's course".
- **Limitations [STATED].** The angle "is not correct as we don't consider the next element"; tributaries "don't affect this segment at all"; "I didn't get any Math classes besides of school, so it took me a lot of time"; "every time I try to create a post I stuck for a week or more with rather insignificant enhancements". Download via d3-save-svg has "some issues with layers".

### 2.7 Heightmap rendering — 2017-06-17 — https://azgaar.wordpress.com/2017/06/17/heightmap-rendering/ — rendering
- **Rationale [STATED].** "Most map generators consider heightmap as a technical thing only, but I believe it's beautiful as is." Five styles, two optional features, several colour schemes were built; "I need to select only one as I tend to keep things simple"; readers were polled.
- **Polygonal [STATED].** Fill each polygon by height. Land is 0.2–1, water 0–0.19. Drawing all ~9k polygons is not an option in SVG ("becomes extremely laggy with a lot of elements"); "even 1.5k land polygons is too much". Colours: D3's Spectral and RdYlGn, reversed (colour of 1 − height) so mountains are not green. Anti-aliasing seams between polygons: a 0.7 stroke hides them but overlaps break the shapes; `shape-rendering` set to optimizeSpeed is faster and seamless but imprecise; filled-fast plus stroked-precise doubles the elements. He keeps overlapping strokes for now, optimizeSpeed "for a big maps".
- **Triangled [STATED].** Polygons are too big, so split each into triangles: not Delaunay (same size as polygons) but two triangles per Voronoi edge using the left/right cell references D3 already gives; triangle colour is the own-cell colour interpolated one third toward the opposite cell's. Result "very smooth, maybe even more than I want"; add a naive 3D cue: right-side triangles darker when lower than the left-side one, stronger at height. Slower (more elements), but good at all scales.
- **Contours [STATED].** Polygons are too coarse for contouring, so rasterise to a 1:1 pixel grid (640×360 in the test, ~230k points). Per-point nearest-polygon lookup is "extremely ineffective"; instead, since sites' coordinates and heights are known and Poisson-disc sampling guarantees a minimum site spacing of about 4 points, assign each site's height to its grid cell and the 8 direct and 18 indirect grid neighbours (27 points per site), then look up only the remainder. Optional Simplex noise (Jonas Wagner's library) over the height array "adds some diversity into a terrain build on just a dozen of blobs". d3-contour (marching squares) with a threshold every 0.04 over 0.2–1 (~20 layers), coloured with the same schemes; a shade copy of each layer drawn just before it, darkened in HSL and offset slightly, gives a 3D effect; the zoom handler shrinks the offset and raises shade opacity so the map is "almost flat on a big scale and got 3D looking on zooming out". Step 0.01 is still only 160 elements. "I would prefer more relaxed lines."
- **Noisy [STATED].** Contouring with the height array multiplied by random 0.95–1.05; too noisy for shades, natural when flat.
- **Pixel [STATED].** 4×4-point blocks as pixels; "don't like the result".
- **Features [STATED].** Slope hatching after O'Leary: his big polygons with similar slopes "are not eligible for this kind of shading"; would need a jittered regular grid; main problem "incompatible with scaling". Gaussian blur filter: works for the polygonal style but fuzzy and slow; useful for relief shading, coastline and river shades.

### 2.8 Biomes generation and rendering — 2017-06-30 — https://azgaar.wordpress.com/2017/06/30/biomes-generation-and-rendering/ — Biomes, rendering
- **Approach [STATED].** All the tutorials he cites (Gallant, Turner, Patel, Waters, Cepero, Cartographers' Guild) use the Whittaker diagram (biome from mean annual temperature × precipitation), "very convent to use in a procedural generation": define precipitation and temperature per polygon, build an own diagram, look up. Precipitation comes from the river-systems model (§2.5).
- **Temperature model [STATED].** Islands of roughly 100k km² (Ireland/Iceland class) have climates "profoundly impacted by ocean temperature, not by the latitude": not "a warm South and a cold North" but "a bit warmer coastline and cooler inland areas", so sea temperature is the first key value and elevation the second. He also notes the generator "unintentionally" makes high (volcanic) islands. Average annual temperature (AAT) at sea level = coastal temperature (height 0.2). He compiled a reference list of European coastal cities, one per Celsius degree from 0 to 19 °C, with altitude and precipitation from climatemps.com (a 20-row data table; not reproduced). Standard coastal value 10 °C; normal deviation ±5 °C; extreme ±10 °C; "semi-random temperature for each map" from these ranges. Lapse rate 6.5 °C/km with 1 km peaks gives only ~6.5 °C across the map, "too low for a fantasy world"; rather than break "the basic laws of nature" he raised the peaks to 2 km so the delta doubles: with 10 °C at the coast, mountaintops reach about −3 °C, above the snow line. Formula: cell temperature = coastal temperature − (height − 0.2) × 20, with coastal temperature a user value in 0–20 and heights 0.2–0.8 (so 0.01 height = 0.2 °C; maximum delta 13 °C). Elevation in metres for display only: height × (height − 0.195) × 4000 (4 m to 1936 m; quadratic "to change the altitude more drastically on the mountains"); depth formula given for reference, unused.
- **Precipitation levels [STATED].** Raw precipitation fitted into a 0–9 scale (he writes that the most arid cells get level 9 and the wettest level 0); for display raw × 500 cm, so 0.01 raw = 5 cm and the maximum ≈ 700 cm.
- **Biome matrix [STATED].** Whittaker's triangle of 8–10 biomes is "too low for me and triangle shape is not very convenient for programming"; he builds a rectangular matrix of ~20 biomes (22 ids, 0–21, from hot desert through glacier) with intermediate types — "I could safe some time using more appropriate Holdridge life zones … but I noticed it too late". Axes: 10 precipitation levels × 100 temperature columns; 100 is wider than the actual 60-point height span so the scale can be shifted for different coastal temperatures by height × 100 − (coastal temperature − modifier)/0.2, with the modifier set to 12 "to get snow at sub-zero temperatures and hot deserts at highest values". Built first as a 100×10 Excel table, then a JSFiddle "biomes workshop" with colour interpolation/smoothing helpers. Colours guided by satellite imagery and mapmakers' conventions; wetter = more saturated; a snow-white/rocky-grey band for cold. (The biome id/name/colour table is a palette; not reproduced.)
- **Rendering [STATED].** Polygonal render "could be worse"; matrix smoothed by averaging neighbours 2–3 cycles — "slightly better and still a bit messy"; plain contour style; relaxed contours (every fourth point, D3 interpolation) "super-messiness" until the layer count is reduced ("organic forms, but there are some rudiments"); triangled style "Much better!". A global-warming animation sweeps coastal temperature 0→25 °C.
- **Limitations [STATED].** "The classification I made is messy and illogical, detailed in some places and too general in others. I was focused mostly on colors"; "I don't plan to use biomes as a main layer"; temperature should also affect rivers and sea ice.
- **Plans [STATED].** A built-in custom colour-scheme module (not high priority).

### 2.9 Coastline extension and Heightmap templates — 2017-10-05 — https://azgaar.wordpress.com/2017/10/05/templates/ — Graph, Shape
- **Problem statement [STATED].** Heightmaps "too uniform, all produced islands were perfectly fitted into a volcanic (high) island model"; and coastlines: linear "works perfectly, but I don't like its angularity", curved "too smoothed and 'vanished'", and "the real problem" is that the curve is independent of the graph, so every new element must reconcile graph and drawing. "Frankly speaking, I do not know how to resolve it, but I can try to make a graph much more detailed along the coastline."
- **Coastline extension (re-graph) [STATED].** Build a new point set and a new Voronoi graph with more points along the coast; simply adding points everywhere "significantly slows the map generation and make it slow on zooming and dragging", so additions must be paid for by removals. After the base heightmap, select "coastal" polygons on both sides of the coastline and keep their sites; for each, add one extra point per neighbouring polygon of the same type (ocean or land), placed one third along the connecting line "with a small random swing". Of ~8k polygons ~500 are coastal, typically with two same-type neighbours, so ~1000 points are added. Only 20–30 % of polygons are land; the rest is ocean/lake that is never rendered, so all other non-land polygons are dropped (their potential uses — ocean decoration, sea trade routes — "could be done without the initial graph"); remaining land sites are kept unchanged. ~8k → ~3k polygons; large near-border ocean cells are acceptable because the graph is not used for ocean work; the extended coastal ocean polygons "provide a kind of clip for a landmass". Curved coastlines on the reworked graph now stay close to the structure; "this extension approach looks promising. I may try to detail the graph even more in a future."
- **Templates [STATED].** The original routine becomes the High Island template. Landforms: Mountain (base of every template; flattened by rescaling when no central mountain is wanted), Hill, Pit (negative hill), Range (linear, narrowed hill), Trough (negative range); a dispersion variable for hills controls whether one island or several result. Five templates: High Island (mountain, ~15 hills, a couple of troughs, pits and ranges; "in a rare cases it generates a couple of islands, it's OK as templates are not intended to be something very rigid"); Low Island (same without ranges, rescaled by 0.3 so "having the same coastline, it looks more flat"); Continental Islands (mountain, 5 troughs; "usually produces a one big rugged island"); Archipelago (mountain, ~15 hills, 2 troughs, 8 pits; "usually produces some small islands that look integrally connected"); Atoll (bigger mountain plus custom code raising the mountain's coastal polygons slightly and replacing the interior with a shallow lagoon; "not sure this template is usable as landmass is too small").
- **Plans [STATED].** Random template choice on generation; manual mode with templates or separate landforms; a template editor considered ("templates creation is not super flexible"); moving from JSFiddle to a local machine, code shared when "at least partially finished".

### 2.10 Settlements, Regions, Routes and Labels — 2017-11-21 — https://azgaar.wordpress.com/2017/11/21/settlements/ — Labels, Regions, Routes, Settlements
- **Framing [STATED].** First non-physical post; "I spent months to make it work and didn't save all the materials"; rendering not covered ("the most time consuming thing which is still in progress"). Settlements were dynasty manors; renamed towns and cities (capitals), both "burg" ("I like a historical vibes it brings and its general meaning of a walled town"). Precondition: "at least 500 manors withing 7 cultural areas". Tried "a dozens of variants, including a full economical simulation, but had to simplify the routine to improve the performance."
- **Pipeline [STATED].** (1) Rank land polygons by geographic suitability; (2) place capitals on the best spots not too close to each other; (3) unite capitals by roads; (4) re-rank by the road system; (5) place towns.
- **Geographic score [STATED].** Elevation (mountains score low); biome "not yet implemented" ("lowland desert is not preferable to temperate mountainous forest"); harbour: a coastal land polygon bordering exactly one ocean polygon has "a sheltered haven"; river bonus scaled by flux; extra bonus at confluences and near estuaries.
- **Capitals [STATED].** Sort by score; a minimum inter-capital distance derived from the user's capital count; walk down the list adding each polygon that passes the distance check. "I'm not even sure I can place them better manually"; coastal attraction is strong "but it's hard to imagine an Island capitals located far from a coastline or a major river". ~3 ms.
- **Roads [STATED].** A* between two points, Dijkstra one-to-all. Cost considers distance, elevation ("avoid mountains if possible"), existing roads ("pave a new way only if it's really needed"), existing burgs ("pass through burgs by the way"), region borders ("new border is a new customs duty"), rivers ("towns usually located on a river banks"). "Even a small change in any modifier drastically change the output"; the existing-road modifier was hardest and became a constant: moving along an existing road costs **0.15**, new road creation much more. Dijkstra uniting all capitals at once gave networks "too much aligned to a source cities", so capitals are united one by one; ~85 ms.
- **Towns [STATED].** Each road use increments a per-polygon path counter; road polygons get an "economical" bonus, crossroads more ("a good spot to place taverns"). Re-sort and place towns until the count is reached, *without* a distance check (~500 towns, "too much calculations"); instead mark a chosen polygon's neighbours as used. Placement was "too monotonous" (best spots cluster), so a small random factor is added before sorting; "I have a strong feeling that distance check should work better. Not super happy with the result, but it's still quite good". ~10 ms.
- **Regions [STATED].** One region per capital; "initially regions were considered as areas uniting towns of the same culture, now I'm almost ready concede regions as countries". Each town takes the closest capital's number; each remaining land polygon takes the closest manor's region; a maximum distance to the closest manor leaves "neutral land" beyond it ("good places to add some abandoned ruins or city-states"). Closest-capital regions "look almost the same", so two parameters: disbalance (global randomness) and per-capital power (random, controlled by disbalance); distance to a capital is multiplied by its power, and doubled if the capital is on another island ("it should not be easy for city to get an overseas possessions"). Merging polygons into one region shape is heavy: ~180 ms with rendering.
- **Ports [STATED].** Coastal settlements with a safe harbour are ports; if an island has settlements but no port, the best candidate is promoted or, with no coastal towns, "remove implausible settlements and leave the island uninhabited" so every inhabited island is reachable; a non-port capital gets a primary road to the nearest port of its region. ~5 ms.
- **Secondary roads [STATED].** Every town should be connected ("even a small town is a center of trade and craft") but without turning the map into a mess. Dijkstra over all towns produced tree-like, river-like networks and could not be tuned; final approach: trunk roads via the capital-road algorithm, then connect each unconnected town to its nearest polygon on the network. "Simple routing and not a great result, but pretty good in general"; ~180 ms.
- **Sea routes [STATED].** Cabotage plus inter-island routes; because redundant sea polygons were removed by the re-graph, all ports can be connected at once with Dijkstra from one start port, with "a significant penalty for a new route element creation" to avoid mess. One mandatory route per island to the biggest island; islands are inter-connected only if both have at least 4–5 ports. Bug: connecting every port to the island's first port leaves a gap on the far side; fix: find the most distant port and, if the network path costs at least 4× the direct route, add the missing route — "quite complicated and resource demanding"; ~50 ms. Feedback that routes hug the coast is accepted: "cabotage routes have to follow a coastline and I don't have an easy way to outline it further."
- **Names [STATED].** Earlier a premade historical list per culture (fine for the Dynasty project); for the generator names must be procedural: a Markov chain trained on a real-world English town-name archive (his gist), giving letter-to-letter probabilities. Rules: no three consonants or vowels in a row; space as word end, accepted once the name has ≥3 letters; maximum seven letters. Region names: a generated name or the capital's name with the vowel ending replaced by or appended with the Latin suffix -ia, used for about 60–80 % of regions; own suffixes or roots like -land/-stan "for a future".
- **Labels [STATED].** Town labels placed above icons "not considering any features or possible intersections"; workaround: labels draggable and editable. Region labels at the pole of inaccessibility of the region polygon via Agafonkin's polylabel (~50 ms).
- **Comments (method-relevant).** Export: "New version with normal svg/png export is coming!" (2017-12-04). ### 2.11 Templates implementation and Heightmap editor UI — 2018-02-08 — https://azgaar.wordpress.com/2018/02/08/templates-implementation-and-heightmap-editor-ui/ — Shape
- **Rationale [STATED].** Default generation picks a semi-random template; "most people don't go deep"; others need a UI "to create really unique and desired maps" and to "create and share their own Heightmap templates". UI "is the most time-consuming process"; a step-by-step "generation journey" was started and abandoned for a usable Demo UI.
- **Template DSL [STATED].** A template is a list of steps over nine elements: Mountain (big round centred blob, once only), Hill, Pit (round depression), Range (elongated), Trough (elongated depression), Strait (centred vertical elongated depression), Add (± a value to all heights), Multiply (all heights × factor), Smooth. Steps carry element-specific parameters; e.g. Hill has count and distribution, where distribution is the padding from the borders (0 none, 0.5 exactly the centre); parameters may be intervals from which a value is drawn per generation; all elements except Mountain can repeat. Six named templates are given as step lists (Volcanic Island, High Island, Low Island, Continents, Archipelago, Atoll); they combine a Mountain with hills/ranges/troughs/pits, Add/Multiply rescales (e.g. land multiplied below 1 to flatten; the Atoll multiplies the interval 0.27–1 by 0.1 to hollow the ring) and a Strait of width 2–8 for Continents (full recipes not reproduced). "Any template is an simple algorithm … I hope readers will compose better templates than the ones I use now." Editor: add, reparameterise, reorder, delete steps; execute any time; save/load "works properly only in Chrome".
- **Brushes [STATED].** Elevate, Depress, Align (set to the first tagged cell's height), Smooth (neighbour average), Hill, Pit, Range (two clicks), Trough; "Brush power" is the initial height applied to the first cell of a sequence. Whole-map buttons: raise ×1.1, lower ×0.9, smooth. Recommended workflow: template draft, then brushes to fine-tune. After customisation the generator "will complete the map in an automatic mode, there is not direct control allowed as of now".

### 2.12 Polygonal rivers and river editor — 2018-02-12 — https://azgaar.wordpress.com/2018/02/12/polygonal-rivers/ — Rivers, UI
- **Rationale [STATED].** Rivers "are still a weak point"; segmented strokes look wrong in vector editors; "consider rivers not as strokes, but as polygons filled with color". Took "about an hour" once tried, following Scott Turner's description.
- **Method [STATED].** Keep the point set and meander amendment; interpolate to a curve; read its total length; step along the length one unit at a time, take the direction from points slightly before and after, and place a point on each side along the normal at an offset that grows with distance travelled (he recommends a hyperbolic-tangent-like growth; the snippet uses an arctangent of length over a "widening" constant of 200 [SHOWN]); left points are collected source→mouth, right points mouth→source so they join directly; add the exact end point so the last fraction of the river is not lost; interpolate each side and join into one path. The old confluence alignment is dropped ("not ideal and effect was really subtle"); a confluence check adds extra width "depending on the confluence 'volume'".
- **River Editor [STATED].** Click a river to show red core points; drag whole river or single points; tools: Resize (rotate/scale), Regenerate (re-randomises width), Add point, Remove point, Copy, Remove, New River (click points, click a point or the course to finish). Editing "does not affect graph structure, just a visual change".

### 2.13 Image to Heightmap converter — 2018-02-26 — https://azgaar.wordpress.com/2018/02/26/image-converter/ — Shape, UI
- **Rationale [STATED].** Templates suit random maps; some cartographers "want to recreate a pre-designed heightmap" (Westeros, Europe) or test maps drawn in GIMP/Photoshop and "use the generator to place rivers/towns rationally".
- **Method [STATED].** Upload via FileReader; draw to a canvas; read ImageData; compute the Voronoi diagram; sample the image colour at each site; fill each cell — a "stained-glass" image. Map colours to his blue-to-red spectral height scheme (~100 colours). No automatic solution is possible for arbitrary colour schemes; images fall into four groups (not maps; maps without elevation coding — separate land from water at best; colour-coded elevation — height by hue; monochrome heightmaps — height by lightness), so two of four can be auto-assigned. Convert RGB to Lab (D3): L for monochrome; a combination of a and b for coloured maps. Auto-assign by **hue**: normalise b + a/2 over [−50, 200], "kind of magic", mainly to send bluish colours below 0.2 (ocean); by **lightness**: normalise L over [0, 100]. Uploads are stretched to 16:9 (resize beforehand). Quality depends on graph size (8k vs ~70k polygons shown). **Manual assignment**: too many colours, so quantise — modified median-cut (MMCQ, Nick Rabinowitz's quantize.js; "some bugs"), fed with one colour per polygon, deduplicated; default **12** colours (adjustable; some images need 2–5). UI: quantised render, "Unassigned colors" list, click a colour then a height on a scale, or auto-assign by lightness/hue, then fix manually; semi-transparent source overlay; then fine-tune or complete.
- **Reflection [STATED].** "I cannot stop thinking all my efforts with random shapes were in vain. Even UI is still poor I consider Image converter is one one the most useful tools I ever made." Released as v0.52b.
- **Comments.** Biomes "already developed, just not added to the demo" (2018-03-09). Globe projection: "Not sure a lot of people need it, and it's really challenging" (2018-03-11); "I will consider the 'Globalization' for the future. I want to try a regular 3D map first" (2018-03-12). Tectonics: "too hard to make interesting shapes via a plausible tectonic simulation"; wind: "planning to add a customizable wind simulation based on boids model … not a priority" (2018-04-22). 3D: simple heightmap visualisation like the three.js terrain example (2018-05-03). A commenter notes "1 pixel is equal to 3 km" (2018-05-03). Converter path in the UI (2018-06-11); all colours must be assigned before completing (2019-06-26); preview resolution is one cell per pixel (2019-10-06); Discord and a tutorial playlist (2021–2022).

### 2.15 Map scale — 2018-07-05 — https://azgaar.wordpress.com/2018/07/05/map-scale/ — Scale, UI
- **Method / rationale [STATED].** Scale = ratio of map distance to ground distance; "A plausible world cannot be built without a scale nominated"; a Scale Editor for units and "scalable parameters". Unit free (km, miles, leagues, stadions, fictional); mile as default because "most generator users are from the United States" and "mile is an ancient unit and hence it has some fantasy vibes". Maps should be continents, not islands; the map is fitted to the screen, so the pixel count varies (iPhone 8 1334 px; 4K ~4000 px); with ~30–40 % land, a default of **3 miles (~5 km) per pixel** gives ~4k miles across on a phone, ~12k on 4K, and on the most common 1366×768 a land extent of ~1400×800 miles (~2200×1300 km) — "quite a small continent, something like a western part of Europe, but I find it acceptable". Measurers: ruler (linear), opisometer (curve), planimeter (area), any number, draggable; road selection shows distance. Area unit: squared distance unit ("sounds too modern" but universal, with the ² symbol). Scale bar must show a round number and redraw on zoom. Population rate: how many people one population point represents; points "calculated based on various geographical and economical factors. The calculation system is not yet finished, I would like to extend it with biomes and trade". Urbanization rate: multiplier for burg population; pseudo-medieval target ~5 % urban and total density not above 20 people per square mile; both configurable.

## 3. Evolution of the core techniques across posts

### 3.1 Spatial graph and sampling
**Takeaway [STATED unless marked].** Relaxed Voronoi chosen over noise and over regular grids for plausibility (2017-03-30); one Lloyd pass judged enough for looks, then found insufficient for pathfinding and polygon drawing, which would need "up to 20" passes, so Poisson-disc sampling replaced relaxation (stated in the edited Voronoi post; in use by 2017-06-17, when the contour renderer relies on its ~4-point minimum spacing); the coastal re-graph (2017-10-05) keeps coastal cells on both sides, inserts 1/3-points with jitter, keeps land and drops the rest of the ocean, taking ~8k cells to ~3k; the sampler's minimum distance is 5.9 and ~8k is the budget that "still runs smoothly in my browser" (2017-04-01; comment 2017-11-21); 30k cells were tried and found "too unpredictable in term of bugs". The author never used the Delaunay triangulation in this era though he states that using both would be best.
- Code-only continuation [SHOWN-code]: jittered square grid from v0.59.12b (2018-09-05, local repo b1309eae); Delaunator from v0.8.0b (2019-04); the 2019-10 sampling-comparison gists. These post-date the blog.
- **Earlier inference revised.** The first pass inferred the jittered grid "won because it gives near-uniform cell size … for a per-cell rain model"; the author's stated reason for leaving pure randomness was pathfinding/drawing regularity, and his stated reason for the re-graph was coastline fidelity and the cost of ocean cells [STATED]. The uniform-cell rationale for the later grid remains [INFERRED].

### 3.2 Heightmap
**Takeaway [STATED].** Blob diffusion with a decrement and a sharpness modifier (2017-04-01) → one big sharp blob plus ~10 smooth hills (same post) → templates composed of Mountain/Hill/Pit/Range/Trough (2017-10-05) → a nine-element step DSL with Strait, Add, Multiply, Smooth and a template editor, plus eight brushes and three whole-map buttons (2018-02-08) → image import with Lab-based auto-assignment and MMCQ quantisation (2018-02-26). Stated constraints: noise never tried ("not a priority"); all borders must be ocean ("a system restriction", 2018-05-08 comment); the whole heightmap must generate in "about 300ms" (2017-10-25 comment), which is why tectonics were rejected; the author later doubted random shapes altogether after seeing converted real-world maps (2018-02-26).
- [SHOWN-code] retained: 0.1b peak heights and decrements; template-primitive internals (0.50b); the 0.53b perspective view and 0.59b templates (Changelog).

### 3.3 Coastline and features
**Takeaway [STATED].** Sea level fixed at 0.2 for the look of the Spectral scale and to keep "a small margin" of water heights (2017-04-03); features by flood fill from the top-left corner (Ocean, then numbered Lakes/Islands) and coastlines chained into closed rings per feature, lakes styled differently (2017-04-03); curves kept but reconciled to the grid by an SVG mask rather than clip paths (too slow) (2017-04-03); the remaining mismatch between curve and graph resolved by densifying the graph at the coast (2017-10-05). The author's explicit constraint: objects (ports, estuaries) are placed on coastline edges, so the drawn coast must not drift from the graph.
- [SHOWN-code] retained: ocean "distance from land" rings for shallow/deep shading (2017-10 gist; "Ocean layers selection" 0.49b); 0.58b lake rework (consistent with the stated 2018-01-25 plan to turn depressions into lakes after routing).

### 3.4 Precipitation, temperature and biomes
**Takeaway [STATED].** The precipitation model was wind-marched from the windward border with random side-walk, loss over land, total loss at mountains (rain shadow), per-wind division and neighbour smoothing (2017-05-08) — chosen as a simpler stand-in for Turner's wind model, which "requires more detailed map". Temperature (2017-06-30) is island-style: a coastal AAT (default 10 °C, ±5 normal, ±10 extreme) minus a lapse term of 20 °C per unit height above 0.2, with peaks deliberately treated as 2 km so the map spans ~13 °C and gets snowcaps; biomes from a 100×10 rectangular matrix (22 ids) indexed by height-derived temperature and 10 precipitation levels, shifted by the coastal temperature and a modifier of 12. The author states he was "focused mostly on colors", the classification is "messy and illogical", and biomes are not a main layer. Comments confirm the biome layer was "developed, but not implemented to demo" (2017-12-09; 2018-03-09) and promised for "the next release" (2019-02-14, 2019-03-02, 2018-12-23); a latitude gradient with Southern/Northern/Equator options (2017-10-25) and a boids-based wind simulation (2018-04-22) were planned. The author acknowledges "a new wind model (looks cool works bad)" in October 2017.
- [SHOWN-code] retained: the gist's constant-rain variant (0.1 south / 0.07 north, ×0.97 downhill decay) is what the *demo* ran in 2017–2018; biomes layer first shipped 0.7a (Changelog).
- **Earlier note corrected**: §3.5 of the first pass called the method "only known second-hand"; it is fully stated, and the third-party summaries were accurate.

### 3.5 Rivers
**Takeaway [STATED].** Fixed from 2017-05-08: lowest-neighbour routing after iterative depression raising (+0.01), highest-first flux accumulation, a threshold (e.g. 3), longest-river-wins ids, deltas (several pour cells, large flux) vs estuaries, two alternating meander points per segment. Width: length-only by choice, for smooth width growth on a zoomable map (2017-05-08); combined with rooted flux at confluences, endpoint shifting by half the width difference along the main stem's normal, left/right-bank detection by bisector, render order by accumulated length (2017-05-27); then filled polygons built by walking the curve and offsetting both sides by an arctangent of length, with extra width per confluence "volume", the old alignment routine dropped (2018-02-12). The author's stated 2018 position: width is "based mainly on river length … some complex calculations looks not so good"; height-dependent meandering tried and rejected; lakes from depressions a stated idea (2018-01-25). River Editor edits are visual only (2018-02-12).
- [SHOWN-code] retained: gist thresholds/constants (§2.5), the 0.54b per-vertex polygon simplification and the 0.58b primary/secondary depression passes.

### 3.6 Settlements, regions, ports
**Takeaway [STATED].** Five-step placement (geographic rank → spaced capitals → capital roads → economic re-rank → towns) replaced "a full economical simulation" for performance (2017-11-21). Score factors: elevation, (planned) biome, sheltered harbour = exactly one ocean neighbour, river flux, confluence, estuary; capitals spaced by a count-derived minimum distance; towns without distance checks (neighbours marked used) plus a random jitter the author distrusts. Regions = power-weighted nearest capital with disbalance, overseas distance doubled, a neutral-land cutoff; initially cultural areas, "now … countries". Ports with a promote-or-depopulate rule; capital→port roads. Stated timings: 3/85/10/180/5/180/50 ms. Later editors (capital star button, border brush) and "regenerate all roads at once" preference appear in comments (2018–2019).
- [SHOWN-code] retained: numeric weights, capital power formula, 7 culture centres (gist b4a29df); 0.58b cultures/namesbase editors; v0.7a spread algorithms (Changelog).

### 3.7 Routes
**Takeaway [STATED].** A* pairwise for capitals (one-by-one; Dijkstra all-at-once rejected as source-biased), cost over distance, elevation, existing roads (constant 0.15), burgs, borders ("customs duty"), rivers; economic re-ranking from road-use counts; secondary roads = trunk roads plus nearest-network connection after a Dijkstra attempt gave tree-like results; sea routes by Dijkstra from one port per island with a new-segment penalty, one mandatory route to the biggest island, inter-island links only between islands with ≥4–5 ports, and a 4×-cost gap-fix. Admitted: "Path finding algorithms are slow"; sea-route gaps; coast-hugging accepted as cabotage.
- [SHOWN-code] retained: A* cost constants; "Dijkstra (not used now)" by 0.54b; the 2024 Urquhart rework (outside blog scope).

### 3.8 Names and labels
**Takeaway [STATED].** Markov chain over a real English town-name archive, with no three consonants/vowels in a row, space-terminated after ≥3 letters, ≤7 letters; region names from a generated or capital name plus -ia for 60–80 %; town labels placed naively above icons but draggable/editable; region labels at the pole of inaccessibility (polylabel). The first post's "no auto label-placement system" rule explains the draggable workaround.
- [SHOWN-code] retained: namesbase editor fields (0.58b); curved labels (0.60b Changelog).

### 3.9 Rendering and styling
**Takeaway [STATED].** SVG element count is the governing constraint throughout (9k polygons "laggy", 1.5k land "too much", 2017-06-17; graph size 1 recommended for editing, 2018-05-06). Height colour via reversed Spectral/RdYlGn; five heightmap styles evaluated with the contour style's shade offset tied to zoom; blur and hatching as optional features; the 2018 styling walkthrough uses blur to hide cells, low-opacity monochrome height as a background, drop-shadows on borders and labels, semi-transparent countries, blurred cultures and a grayscale variant. Relief icons are acknowledged as "super primitive … unchanged from the very first generator version".
- [SHOWN-code] retained: relief glyphs as path strings sorted by y with the comment to delete rather than hide for a "fast and clear" map (gist ad0dab4); style-editor parameters and active zooming (Changelog 0.51b/0.53b).

### 3.10 Scale, units and population
**Takeaway [STATED].** Scale separated from geometry as a system parameter with a unit choice (mile default, 3 mi/px), measurers, square area units, a round-number scale bar redrawn on zoom; population points from "geographical and economical factors" scaled by a population rate, with urbanization ~5 % and density ≤20 per square mile as medieval targets; the model "not yet finished", to be extended with biomes and trade.
- [SHOWN-code] retained: population formulas (gist 70ab7ef).

### 3.11 Performance (stated budgets)

## 4. Author's stated philosophy and admitted limitations

### Takeaway
In his own words the generator is governed by four stated commitments — plausible look, speed on generation and dragging, scalability (zoom), ease of coding — and by a willingness to drop anything that costs too much ("I don't need sugar if it costs too much"). Realism is a means: rivers are derived from drainage and roads from costed pathfinding because that *looks* right, while physical simulation (tectonics, full wind models, economic simulation) is rejected whenever it threatens the ~300 ms heightmap or the frame budget. He repeatedly chooses "the easiest algorithm I can imagine" and reports that simpler gave better results.

## 5. Implications for a native SettlementForge world regime

(Judgements are mine; evidence tags refer to §2–§4. Items changed by the full read are marked ★.)

**KEEP**
1. **Rivers as a derived property of the heightmap** (fill depressions → precipitation → route to lowest neighbour highest-first → threshold → longest-wins ids → delta/estuary mouths) [STATED, 2017-05-08]: keep the pipeline semantics; replace the author's iterative raise-by-0.01 fill (which he himself calls ineffective) with priority-flood, and make lakes first-class outputs of the fill — the author's own stated intention (2018-01-25 comment) [STATED].
2. **Mouth typing (delta vs estuary) from flux and the number of pour cells** [STATED]: trivial, decisive; generalise to a few mouth archetypes.
3. **Two-stage settlement scoring (geography, then economy after roads exist)** with spaced capitals and a harbour rule ("exactly one sea neighbour = sheltered haven") [STATED, 2017-11-21]: this is the manor ranking SettlementForge needs; keep the harbour/estuary/confluence/crossroads vocabulary; ★ also keep the author's own second thought — a distance check for towns "should work better" than neighbour-marking plus jitter [STATED].
4. **Route costs that encode politics** (border = customs duty; road reuse at a flat 0.15; river-bank and burg pass-through bonuses) [STATED]: keep as cost-model vocabulary; ★ the author's stated failure modes — one-to-all Dijkstra biases toward sources, all-pairs A* is slow, tree-like secondary networks — argue for a neighbourhood-graph (Urquhart/RNG) base, which the author adopted only in 2024 [SHOWN-code/Patreon, outside scope].
5. **Template DSL of heightmap primitives** (Mountain, Hill, Pit, Range, Trough, Strait, Add, Multiply, Smooth; distribution padding; interval parameters) as a user-editable step list [STATED, 2018-02-08]: keep the semantics and the author's workflow (template draft → brushes).
6. **Label placement at the pole of inaccessibility** for regions [STATED]; keep. ★ Note the author never built automatic town-label placement by principle ("too hard … to make it fast") — SettlementForge should budget for it rather than inherit the draggable workaround.
7. **Explicit scale layer** (unit, distance per pixel, square area units, round-number scale bar, population rate, urbanization) separate from geometry [STATED, 2018-07-05]: keep; 3 mi/px, ~5 % urban, ≤20 per sq mi are usable medieval defaults.
8. ★ **Sea-route rules** (cabotage along coasts, one mandatory route to the largest landmass, inter-island links only between well-ported islands, gap detection by cost ratio) [STATED]: keep as the vocabulary of a port network.

**GENERALIZE**
1. **"Sample where information lives"** — the coastal re-graph (densify the coast, drop open ocean) [STATED, 2017-10-05]: generalise to densifying coasts, rivers and settlement zones on a resolution-independent base; the author's own stated reason (drawn curves must not drift from the graph where objects are placed) is the requirement to preserve, not the Voronoi mechanism.
2. ★ **The precipitation model** — the wind-marched cloud walk with rain shadow [STATED, 2017-05-08] is already the shape SettlementForge wants; generalise to a per-cell moisture input contract with several prevailing winds and the author's planned latitude gradient (S/N/Equator options) [STATED, 2017-10-25].
3. ★ **The temperature/biome contract** — coastal AAT ± deviation, lapse by height, a rectangular biome matrix indexed by temperature and moisture levels with a shift parameter [STATED, 2017-06-30]: keep as a configurable table; replace the island-only "coast warm, inland cool" assumption (the author chose it because his maps were ~100k km² islands) with a latitude-plus-continentality model, and prefer a Holdridge-style grid, which the author says he "noticed … too late".
4. **Markov name generation with phonotactic constraints** (no triple consonants/vowels, length cap, culture suffix rules) [STATED]: generalise to per-culture name bases with the same constraint vocabulary.

**REJECT**
1. **Blob-diffusion heightmaps with a sharpness modifier and parent-based ridge sprawl** [STATED]: visually dated and resolution-dependent (the author himself notes the look "depend[s] on the graph size" and that converted real-world maps made him doubt random shapes); keep only the DSL semantics on top of a resolution-independent field.
2. **Width from river length** [STATED, chosen for smooth zoom]: reject for SettlementForge — the author's reason (SVG stroke jumps on zoom) does not apply to a data-driven renderer; emit discharge-based widths with hydraulic-geometry smoothing.
3. **Per-pixel polygon construction by walking the curve** [SHOWN, 2018-02-12]: the author simplified it within seven weeks (0.54b) [SHOWN-code]; emit widths per vertex.
4. **Nearest-of-N cultures and nearest-capital regions** (power-weighted) [STATED]: the author replaced them with spread algorithms in v0.7a [Changelog]; do not adopt the 2017 version.
5. **Hard-coded sea level 0.2 chosen for a palette** and **all-borders-ocean as "a system restriction"** [STATED]: make both world parameters.
6. **SVG-DOM rendering of cells** and the element-count ceiling that drove most compromises (clip paths, blur, graph size 1) [STATED]: render from data.
7. ★ **Depopulating an island that has no viable port** ("remove implausible settlements and leave the island uninhabited") [STATED]: a shortcut to guarantee trade reachability; SettlementForge should instead record unreachable settlements as a property.

**REPLACE**
1. Iterative +0.01 depression raising → priority-flood with lake outputs [STATED limitation + stated plan].
2. Threshold on an unscaled flux ("e.g. 3", then 0.85 in code) → discharge in physical units derived from precipitation × area.
3. Confluence-only width recomputation and endpoint shifting [STATED, 2017-05-27] → continuous width from discharge; keep the author's left/right-bank test only if tangential junctions are needed for drawing.
4. One-by-one A* for capital roads [STATED, slow] → shortest paths on a neighbourhood graph with the same cost vocabulary.
5. Lab-hue "magic" for image import [STATED] → explicit user-declared legend mapping with the author's quantise-then-assign UI pattern retained.
