## 1. Summary

Azgaar's Fantasy Map Generator was first published as a bl.ocks gist on 2017-03-20 and reached its repository form in late 2017/early 2018 [STATED, CL:509-511; SHOWN, git 6859d902 "1st code commit (wip)" 2017-10-09]. Its history falls into five eras: (a) the **0.4x–0.61 beta** (2018), a single-file D3/SVG app accreting editors (countries, burgs, rivers, routes, cultures, namesbase, relief, markers) and the heightmap template system; (b) the **0.7a/0.8b/0.9b** rework (April–June 2019) that introduced world size, climate, biomes, biome-dependent population and a new cultures/states spread algorithm, and which also became the floor for save-file compatibility (`v0.70.0`) [STATED, CL:5]; (c) **v1.0–v1.4** (Aug 2019–mid 2020) adding provinces, religions, diplomacy, zones, 3D/globe, military, battles and ice; (d) **v1.5–v1.9** (2021–2023) adding emblems/Armoria, a rivers-and-lakes hydrology rework that moved river data out of the SVG, markers, submap/transform, PWA, hierarchy trees, charts, a climate rework and the long 1.8x point-release stream; and (e) the **v1.99 → v1.154** acceleration (Aug 2024 → Oct 2026) in which routes, zones, labels, ice, measurers, relief, biomes, styles and layer state were each moved from "the SVG is the database" into explicit data, the codebase migrated to Vite/TypeScript (Jan 2026, "FMG 2.0"), and large new subsystems landed: burg groups, economy (goods/markets/trade/taxes), journeys, a declared generation pipeline, an Electron desktop app, an Omnibar, a Wrap tool, a feature-level coastline editor and a map-reading AI assistant. Old `.map`/`.gz` files from v0.70.0 onward are migrated on load by an ordered chain of version-gated steps [STATED, CL:5; SHOWN, AU:94-100], and the stated end-state is a single JSON `map` object with data separated from rendering [STATED, ARCH future-data-model.md:1-3; ARCH architecture.md "Goals"].

## 4. Data-model and `.map`-format changes, with migration notes

**Migration mechanism [SHOWN unless noted].**
- Compatibility floor: "Compatible `.gz` and `.map` files from `v0.70.0` onward are checked and auto-updated when loaded. Maps older than `v0.70.0` are considered ancient and require the matching old Generator version" [STATED, CL:5-7]. Load compares the file's version to `0.70.0` and shows an "ancient" message linking to the changelog archive list; a file newer than the running version is refused with a "newer than the current version" message [SHOWN, LOAD:159-160, 230-235].
- Version strings are parsed from the legacy `0.7b`-style form, validated, and compared by major/minor/patch; the update window is shown when the stored version is older at major.minor [SHOWN, VER:40-71, 112-162]. A "version control for updates and save/load" first appears in 0.52b [STATED, CL:478].
- The migration is one ordered function (`resolveVersionConflicts`) that walks `isOlderThan(<version>)` gates from 1.0.0 up to 1.154.1; later gates assume earlier ones ran (the 1.139 biomes step is deliberately hoisted first "because older migrations consume biome data") [SHOWN, AU:94-131].
- `.map` is a line/pipe-delimited positional format: `data[1]` settings (now a JSON object, formerly pipe string), `data[3]` biomes (string or JSON array), `data[5]` the SVG, `data[6]` grid, `data[7-11]` typed grid arrays, `data[12-15]` features/cultures/states/burgs, `data[16-27]` typed pack cell arrays, `data[29]` religions, `data[30]` provinces, `data[32]` rivers, `data[34]` fonts, `data[35]` markers, `data[36-37]` cell routes/routes, `data[38]` zones, `data[39]` ice, `data[45]` goods uploads (now written empty), `data[50]` layers state, up to `data[52]`; `data[23]`, `[28]`, `[33]` are deprecated slots (old `cells.road`, `cells.crossroad`, rulers) [SHOWN, LOAD:266-360; AU:+227, 1578]. The creator calls this "a stack of accidents" [STATED, UPD v1.149.0:72].
- Gzip: compression was shipped in 1.93.00 and rolled back in 1.93.02 for time cost and browser support [STATED, CL:173-174]; load still accepts gzip-compressed input [SHOWN, LOAD:174, 212].
- Partial regenerations and the auto-update migrations "do not replicate the pipeline, but they belong to the same dependency graph"; adding a generation step requires an auto-update migration so older saves gain the new fields [STATED, ARCH generation-pipeline.md:204-208, 222-223].

**Target model.** The future `.map` is "a valid JSON capturing all data required to render and operate the map, including UI and style settings… a single gigantic object `map`" with `meta` (initial/current version, revision), `facts` (seed, graph size, geography, climate inputs, lore, units, style preset, groups, transports, coastline settings), `layers` (order/active), `style`, and `data` (topology, geography, states, cultures, religions, settlements, annotations); the example version strings are in the 2.x range [STATED/SHOWN, ARCH future-data-model.md:1-204]. The current data-model doc is described as "inconsistent and not well-documented" [STATED, future-data-model.md:1]. The invariant is that "Saving a `.map` file MUST preserve the exact world state so it can be reloaded identically" [STATED, CTX:69].

## 6. The FMG 2.0 transition

- **When:** NPM/Vite migration merged 2026-01-22 (#1266, SheepFromHeaven) with the changelog warning that the tool can no longer run without a build step and uses TypeScript for some files [STATED, CL:135-140; SHOWN, git 9e0eb036]. Module ports then ran continuously from 2026-01-26 (#1273) through 2026-10 [SHOWN, git 29bc2832…]. The creator says the migration "has run alongside feature work since January 2026" [STATED, UPD v1.149.0:106].
- **Why:** nothing was type-checked, everything could reach everything, nothing could be tested, and above all "the generator has been using its own drawing as a database. Every rendering change becomes a complex data migration… .map file has to be bigger to contain the whole rendered svg, and save file format itself is just a stack of accidents" [STATED, UPD v1.149.0:62-74].
- **How:** "the tool must keep working at every step. Each module is ported in place, with a small compatibility shim" [STATED, UPD v1.149.0:78]; the migration guide prescribes layers (`generators/`, `renderers/`, `controllers/`, `components/`, `services/`, `data/`, `utils/`), named exports, functions over classes, D3 v7 named imports, modules that own and tear down their DOM, lazy-loaded controllers, and a temporary `window` bridge to be deleted when every caller is TypeScript [STATED, ARCH migration-guide.md:7-36, 104-292]. CONTEXT.md fixes the FMG 2.0 rules: generators must not touch SVG/DOM; generators and editors mutate state, renderers react; renderers stateless/idempotent; whole world state serializable to one JSON [STATED, CTX:27-33].

## 7. Implications for a native SettlementForge world regime (per subsystem)

Verdicts: KEEP (adopt as a requirement), GENERALIZE (adopt the idea but widen it), REJECT (do not carry over), REPLACE (own mechanism). Reasoning is mine [INFERRED] unless it quotes a stated FMG lesson.

| Subsystem | Verdict | One-line reasoning |
|---|---|---|
| Heightmap templates + image import + pre-defined real-world heightmaps | GENERALIZE | FMG needed four iterations (0.50b templates, 0.52b images, 1.732 real-world, 1.84 preview) to reach "see it before you generate"; PLAT should take a declarative terrain-recipe input with preview from day one, not a template DSL tied to one editor. |
| Voronoi/packed-cell graph | REPLACE | FMG's `grid`→`pack` repack "invalidates every earlier pack cell index" (generation-pipeline.md:68) and forced UINT16 and precision fixes; a settlement engine needs a stable, addressable spatial index with settlement-scale resolution rather than a world-scale repack. |
| Features/coastline (fractal roughening, per-feature settings, position-keyed determinism) | KEEP | The 1.119→1.153 lesson is that roughness must be keyed to map position so local edits don't ripple; PLAT coastlines/shore detail should be seeded by location for the same reason. |
| Climate (latitude/altitude temperature, wind-driven precipitation, pole controls) | GENERALIZE | FMG's climate is a thin band model that was patched repeatedly (tropical belt, pole asymmetry, desert rule); PLAT only needs a climate *input* contract (temperature/precip per cell plus seasonal curve like the 1.72 burg graph) that any upstream model can satisfy. |
| Rivers & lakes (flux, dynamic lake type, Penman evaporation, depression handling) | KEEP | This is the most method-explicit and stable subsystem (1.6/1.62/1.65), and its output (flux, confluence, navigable rivers) directly drives ports, routes and economy in later versions. |
| Biomes + custom biomes + relief pools | GENERALIZE | Biomes are the hub that population, goods, relief and movement cost all read (pipeline table); PLAT should treat biome as a typed land-use class with editable derived rules (relief pools, movement cost, habitability) rather than a fixed 13-row table. |
| Population ranking (habitability score → rural pop) | GENERALIZE | FMG's `rankCells` folds biome, flux, elevation, coast and goods into one score; PLAT should expose the same factors as a pluggable suitability function since settlement placement is its core concern. |
| Cultures (spread, hierarchy, namesbases) | KEEP | Namesbase-driven naming has survived unchanged since 0.58b and multi-parental hierarchies (1.86) are a cheap, requested feature; a settlement engine needs culture to pick names, shields and burg styles. |
| Burgs (groups, rules, lock, ports, preview link) | KEEP → core | 1.109 burg groups with rule-based grouping (population percentile, biome/state/culture, port/capital/temple) is exactly the classification PLAT must own; locking (1.61) and regeneration are mandatory editor semantics. |
| States, provinces, diplomacy | GENERALIZE | Needed as context (taxes, borders, forms) but PLAT should consume state/province as external polygons/ids with lock semantics, not re-implement expansion; FMG's own expansion needed RNG-stability fixes as late as 1.122. |
| Religions | REJECT (as generator) / KEEP (as attribute) | Settlement maps need religion only as a burg attribute feeding temples and names; the spread generator adds little to PLAT. |
| Routes (Urquhart network, stored cell connections, lockable, navigable rivers) | KEEP | The 1.99 rationale (network not chain; stored data enables trade, travel, population) is precisely PLAT's need; adopt Urquhart-over-Delaunay as the baseline road graph and store routes as cell chains. |
| Military & battles | REJECT | Orthogonal to settlement mapping; can be layered later from the same state/burg data. |
| Markers (typed, config-generated, lockable, radius queries) | GENERALIZE | Treat as a generic typed point-of-interest layer with generation rules and lock, since 1.7/1.139 show users want both automatic placement and manual pinning. |
| Zones | GENERALIZE | A generic region-annotation layer with type filter; FMG only made it data-backed in 1.100, confirming it should be data from the start. |
| Labels (groups, zoom extents, spread/raycast placement, data-backed) | KEEP | Labels took four model changes (1.0, 1.92, 1.113, 1.140); PLAT should start with a flat label-group model carrying zoom extents and a deterministic placement solver. |
| Emblems / icon library | GENERALIZE | The 1.154 icon-library lesson (reference, don't copy; one picker for all slots) applies to every asset kind in PLAT; Armoria-style heraldry generation itself is optional. |
| Relief icons (pools, ordered rules, viewport rendering) | KEEP | Relief rules by elevation/temperature/biome with first-match precedence (1.154) are a clean, stated mechanism for decorative terrain and map well onto settlement-scale decoration. |
| Ice | REJECT | Minor visual layer, repeatedly reduced (1.89, 1.108.3); not relevant at settlement scale. |
| Styles as a validated store with presets and per-value reset | KEEP | 1.150/1.154 moved styling out of the SVG after "several long-standing bugs came from exactly this"; PLAT styling must be a schema-validated record from the outset. |
| Save/load/migration (positional slots, ordered version gates) | REPLACE | FMG's own author calls the format "a stack of accidents" and the future model is a single versioned JSON; PLAT should start with the target shape (meta/facts/layers/style/data) and a version gate per schema change, never positional slots. |
| Export (SVG/PNG/tiles/GeoJSON/JSON) | KEEP | Stable, repeatedly requested, cheap when data is the source of truth. |
| 3D / eroded terrain / satellite texture | REJECT (for now) | Explicitly "view-only… mostly just for fun" (UPD v1.123.0:74); not a world-regime requirement. |
| Editors (shared paint tool, undo, lock, overview tables, Omnibar) | GENERALIZE | The 1.147 consolidation of seven brushes into one and the 1.153 Omnibar show that editor affordances should be shared services over the data model, not per-subsystem code. |
| Assistant (map-reading, before→after proposals with Apply/Undo) | GENERALIZE | The proposal/apply/undo contract (1.154) is a good generic mutation API for any agent or script; the chat UI itself is optional. |
| Economy (goods, markets, single-cycle production, taxes) | GENERALIZE | A one-pass economy with cost-aware market territories is cheap and gives settlements purpose; PLAT should keep goods as a typed catalogue and let the cycle be pluggable, since FMG patched it through 1.125–1.153. |
| Journeys (segments, domains, A* over biome cost, two clocks) | KEEP | Travel-time semantics (travel day vs total time, stay segments) are directly useful for settlement-scale narrative and already consume routes/rivers correctly. |
| Measurers / scale and units | KEEP | Scale bar since 0.54b and data-backed rulers since 1.61; trivial but essential. |
| Generation pipeline as declared, ordered step data with per-step timing and failure naming | KEEP | Stated to have replaced hand-copied call lists in four regeneration paths; PLAT should declare its pipeline and derive erase/regenerate slices from it instead of maintaining parallel lists. |
| Determinism (seeded PRNG everywhere, position-keyed noise, no sort-with-random) | KEEP as hard requirement | FMG kept finding non-determinism a decade in (1.122.6, 1.139 route seed); PLAT should enforce seeded generation and ban randomness in comparators by lint/test. |
