## Executive summary

Azgaar's Fantasy Map Generator is a nine-year-old browser cartography tool (first gist 2017-03-20, v1.154.2 on 2026-10-16) whose core idea has never changed: a jittered-lattice Voronoi mesh carrying a 0–100 height field, from which rivers, lakes, biomes, settlements, states and routes are *derived* in one strictly sequential pipeline, rendered to one SVG, and saved as a 53-field delimited text file that until 2024 used that SVG as part of its database [STATED, UPD v1.149.0:62-74; OBSERVED, SRC/src/generators/generation-pipeline.ts:8-49]. The 2024–2026 era (v1.99 → v1.154) is a sustained, creator-stated retreat from "the drawing is the database": routes, zones, labels, ice, measurers, relief, biomes, styles, layer state and notes were each moved into explicit data, the code was migrated to Vite/TypeScript with 69 test files where "the classic JS had no tests at all", and the generation order became declared step data [STATED, UPD v1.149.0:78-97; SHOWN, CL:88-161]. FMG's physical model is deliberately thin and visual-first: Uint8 heights with sea level at 20 and metres derived by an exponent that is also a display option, a latitude-band temperature model, a row-marched wind/precipitation model that can silently wrap a Uint8, single-flow-direction steepest descent over an ε-relaxed depression fill (not a priority flood), no groundwater, no deltas, and lakes keyed to a −0.1 level hack [OBSERVED, SRC/src/utils/unitUtils.ts:59-72; SRC/src/generators/river-generator.ts:446-505; SRC/src/generators/lakes.ts:12-16]. Its human layers are a one-shot tableau built from two primitives, spaced greedy placement and budgeted typed Dijkstra floods, and the creator says plainly that "the map is static" and the economy "is a single calculated cycle, not a running simulation" [STATED, WIKI/Knowledge Base.md:465, 761].

SettlementForge today embeds a rebuilt, security-hardened `dist` of **upstream v1.114.2 (2026-04-09)** in an iframe, forces it to generate geography only, and never parses its output: the host stores an opaque snapshot blob, a seed, and placement rows, and reads back a one-shot capture of seven pack arrays plus two grid arrays from which it freezes an integer "spatial digest" [OBSERVED, HOST/public/map/versioning.js:19; HOST/public/map/sf-bridge.js:123-150, 1291-1330; HOST/src/domain/spatial/spatialDigest.js:587-916]. The audit's central coherence finding is that **no settlement generation input comes from the map**: terrain, coast/river status, trade access and threat are chosen from config at generation, frozen as "sacred" genesis, and only measured against the map afterwards with an advisory toast and a receipt [OBSERVED, HOST/src/generators/steps/resolveConfig.js:109-207; HOST/src/domain/worldPulse/routeNetworkGenesis.js:6-10]. The host also carries structural debt in the fork itself: its bundle was rebuilt from modified upstream TypeScript source that is not in the repository, contradicting the runbook's claim that the bundle is "FMG-native" [OBSERVED, HOST/public/map/index-Bp79q281.js global-export grep vs STATED, HOST/docs/fmg-fork.md:81-84].

For a fully native SettlementForge world generator on the PLAT architecture (exact integer-centimetre planar kernel, raster D8/priority-flood hydrology, canonical/derived/authored state, persistent addresses, local regeneration, one-way host-to-map flow), the consolidated verdict is: **KEEP** FMG's semantic contracts and process disciplines (land/water features and distance fields, lake open/closed-by-evaporation typing, river threshold/confluence/navigability semantics, biome matrix as a configurable table, suitability-driven burg siting with two-ports-per-water-body rules, Urquhart-over-Delaunay route networks with stored cell chains, label groups with zoom bounds and pole-of-inaccessibility placement, a declared pipeline runner with per-step timing, seeded determinism as a hard requirement, a schema-validated style store, the model-method edit API, lock semantics, and the Assistant's draft/before-after/Apply/Undo transaction); **GENERALIZE** the template DSL into resolution-independent raster operations, the climate model into a per-cell input contract, cultures/states/provinces/religions into host-supplied cost vectors over engine flood primitives, markers/zones into generic typed POI and region layers, and graph overrides into content-matched authored deltas; **REJECT** the Voronoi repack, the SVG-as-state renderer, per-controller redraw lists, id re-indexing on regenerate, session-only undo, the military/battle/zones/economy simulations (host owns them), relief/ice/ocean-ring decoration at world scale, presentation-only 3D, and in-page execution of LLM-written scripts; and **REPLACE** the Uint8 height encoding with integer-centimetre metres on an explicit datum, the ε-relaxation depression fill and single-flow routing with priority-flood D8 on a raster, the unit-less flux/width with discharge and hydraulic-geometry width, the positional `.map` format with versioned id-keyed JSON, and the "regenerate then re-copy by projected position" resample with in-frame re-derivation from boundary conditions. Every blocked source (blog bodies, Patreon, Reddit, YouTube, Discord, the login-walled dev board, the GitHub REST API, two host design documents, the fork's bundle source) is recorded in the limitations section as *blocked, not absent*.

## Nine years in five eras: FMG accreted editors first, then moved its data out of the drawing

FMG's history is a story of a single-file D3/SVG demo that grew editors faster than data model, then spent 2024–2026 paying that debt. The release notes, the 511-line changelog, 36 update documents, 2,593 commit subjects and the public releases pages agree on five eras [OBSERVED, CL; UPD; git log saved at the releases researcher's scratchpad].

**Era A, the gist and the 0.4x–0.61 betas (2017-03 → 2018-11).** The project was "first published" as a bl.ocks gist on 2017-03-20 and reached repository form with a "1st code commit (wip)" on 2017-10-09 [STATED, CL:509-511; SHOWN, git 6859d902]. The devlog (16 posts, 2017-03-30 → 2018-07-05) and the recovered 113-revision gist history show the physical model already fixed by mid-2017: random sites with one Lloyd pass, blob-diffusion heightmaps with a "sharpness" random modifier, sea level fixed at 0.2 "where the green color begins" in the Spectral scheme because that scheme "already looks plausible", rivers computed from drainage over a depression-filled heightmap rather than "random strokes", longest-wins confluences, deltas versus estuaries at the mouth, and a coastal "re-graph" with more points along the coastline that the current docs still cite for repacking [SHOWN-code, gist revs 581c717, abeef6d, a54e23a; STATED-snippet, azgaar.wordpress.com/2017/04/03/coastline/, /2017/05/08/river-systems/, /2017/10/05/templates/; STATED, ARCH data-model.md:12]. The 2017-11-21 settlements post introduced capitals with "disbalance and power", regions first as shared culture and then as countries, and route costs in which a border "is treated as a new customs duty" [STATED-snippet and verbatim quotation in github.com/Flokey82/genworldvoronoi, azgaar.wordpress.com/2017/11/21/settlements/]. The 2018 betas then accreted the editor set: heightmap templates and a Template Editor (0.50b, 2018-02-06), the image-to-heightmap converter and "version control for updates and save/load" (0.52b), countries/burgs/scale editors and a population-calculation change (0.54b), the route editor (0.56b), relief icons (0.57b), cultures and namesbase editors plus reworked lakes (0.58b), random-seed support and the Medieval Fantasy City Generator integration (0.59b), markers and curved labels (0.60b) [NAMED-ONLY, CL:385-497]. The stated project goal in the 0.54b README was a "plausible, fast, interactive" map for a Medieval Dynasty simulator with ≥500 manors in 7 regions over ~200,000 km² [STATED, README at git fa9ec736]; the wiki later records that simulator as "on hold" [STATED, WIKI/Q&A.md:72-73].

**Era B, the climate rework and the compatibility floor (2019-04 → 2019-06).** 0.7a (a separate alpha repository, 2019-04-14) added world size and climate configuration, temperature and precipitation layers, a biomes layer and editor, a biome-dependent population model and a new states-and-cultures spread algorithm, with the only stated rationale being "faster generation and smoother edit experience" [STATED (perf) / NAMED-ONLY (algorithms), CL:371-383]. 0.8b moved it to production and 0.9b added regenerate-burgs/states [NAMED-ONLY, CL:359-369]. **v0.70.0 is the save-file compatibility floor**: "Compatible `.gz` and `.map` files from `v0.70.0` onward are checked and auto-updated when loaded. Maps older than `v0.70.0` are considered ancient" [STATED, CL:5-7; SHOWN, SRC/src/services/io/load.ts:159]. The blog's most-cited post, "Biomes generation and rendering" (2017-06-30), is credited by third parties with a Whittaker-style temperature×moisture model and wind-marched precipitation, but no temperature or biome code exists in any 2017–2018 gist revision; biomes shipped two years later in 0.7a [SECONDARY; SHOWN-code gist history scan; STATED, CL 0.7a] — a documentation-versus-artefact gap to carry forward.

## The physical pipeline: ~40 sequential steps over two Voronoi meshes, visual-first and unit-light

FMG builds a world as one sequential list of ~40 steps over two shared globals: `grid`, a jittered-square-lattice Voronoi mesh of per-cell typed arrays, and `pack`, a second Voronoi mesh built from a subset of grid points plus coastal midpoints, where everything downstream is indexed [OBSERVED, SRC/src/generators/generation-pipeline.ts:8-49]. The declared physical order is `grid → heightmap → markupGrid → depressionLakes → nearSeaLakes → mapSize → temperatures → precipitation → clearPack → clearGraphOverride → regraph → markupPack → defaultRuler → rivers → biomes → featureGroups → ice`, after which the human layers run; relief icons, ocean rings and coastline displacement are *not* pipeline steps but are produced lazily at draw time [OBSERVED, generation-pipeline.ts:8-49; SRC/src/renderers/draw-relief-icons.ts:13; SRC/src/generators/ocean-generator.ts:399; SRC/src/generators/coastline-generator.ts:532]. The creator's design stance is that "the execution order is the dependency graph" and that there is deliberately no declared dependency list, because the sequence "has never been anything but a straight line" [STATED, ARCH generation-pipeline.md:3-7, 48-50].

**Grid and height.** Spacing is derived from the requested cell count (13 density steps mapping 1,000 … 100,000 cells, default 10,000 on a 1280×800 px canvas), points are laid row-major and jittered by ±0.9·(spacing/2) then rounded to two decimals, boundary pseudo-points ring the extent, and Delaunator produces the Voronoi; circumcentres are kept as exact floats because a test guards against the rounding that made cells "blocky" at high counts [OBSERVED, grid-generator.ts:103-149; voronoi.ts:277-433; voronoi.test.ts:377-411; SRC/src/data/graph-density.ts:3-26]. If the tab reports no size the canvas falls back to 1280×800, so **the viewport can change the extent and thus the map** [OBSERVED, options-model.ts:1-3; INFERRED consequence]. Height is Uint8 0–100 with `SEA_LEVEL = 20`; display metres are (h − 18)^exponent with exponent default 2 (so h=20 → 4 m, h=50 → 1,024 m, h=100 → 6,724 m) and water depth is ((h−20)/h)×50 [OBSERVED, SRC/src/utils/heightUtils.ts:2-10; unitUtils.ts:59-72]. The exponent is a *unit option* (1.5–2.2) that nonetheless feeds temperature, precipitation, biomes and lake evaporation [OBSERVED, temperature-generator.ts:137-152; lakes.ts:60-64; STATED, WIKI/Scale-and-distance.md:207] — the single most consequential coupling to avoid in PLAT.

**Heightmap templates.** A template is a script of one step per line over ten tools (Hill, Pit, Range, Trough, Strait, Mask, Invert, Add, Multiply, Smooth), with numeric ranges resolved probabilistically and placement windows as percentages of the extent [OBSERVED, heightmap-generator.ts:12, 67-76, 508-581]. Hills are BFS blobs whose ring contribution decays by a power with ±10 % noise; ranges are greedy noisy ridges between two points with "prominence" spurs; straits are power-law trenches; two cell-count-dependent exponents (blob 0.93→0.997, line 0.75→0.93) keep a feature's *pixel* footprint roughly constant as density changes [OBSERVED, heightmap-generator.ts:28-65, 88-442; INFERRED purpose]. There are 14 named templates with selection weights and 23 real-world grayscale PNGs each pinned to a fixed world size and position; the PNG loader draws the image at exactly cellsX×cellsY so 1 px = 1 cell and applies a soft curve above 0.2 [OBSERVED, SRC/src/data/heightmap-templates.ts:1-181; precreated-heightmaps.ts:8-32; coordinates.ts:11-35; heightmap-generator.ts:583-623]. The wiki says a template is prescriptive but "there is always a significant level of randomness", and the editor refuses to finalise with fewer than 200 land cells [STATED, WIKI/Heightmap-template-editor.md:197; WIKI/Heightmap-customization.md:103].

**Features, lakes, map size.** A stack flood fill from cell 0 groups land (h ≥ 20) versus water; a water group touching the border is `ocean`, otherwise `lake`; land groups are `island`; an outward march marks water −2 … −10 [OBSERVED, features-generator.ts:77-159]. Deep-depression lakes are created for every non-border local minimum whose BFS within `lakeElevationLimit` reaches no water (default limit 20; 80 disables), and near-sea lakes are breached through coast cells with h ≤ 22 [OBSERVED, grid-generator.ts:152-253]. The world box is derived from a per-template size/latitude draw and is plate-carrée: pixel↔degree mapping is linear, the globe view uses an equirectangular projection, and "distortion is the strongest near the poles" [OBSERVED, coordinates.ts:37-100; SRC/src/utils/commonUtils.ts:249-263; STATED, WIKI/Knowledge Base.md:809].

**Climate.** Sea-level temperature inside the tropics is Teq − |lat|·0.15 and linear to each pole outside; a 6.5 °C/km lapse applies to land only, computed per row and stored as Int8 [OBSERVED, temperature-generator.ts:119-168]. Temperature is "an annual average and can only be set world-wide" [STATED, WIKI/Knowledge Base.md:481, 721]. Precipitation re-seeds Alea ("the same winds for the same map, whoever rolled before"), marches six latitude-tier winds along grid rows and columns with an 18-entry latitude modifier table, drops humidity with an orographic term, adds a `rand(10,20)` coastal bonus, dumps everything at barriers above h 85, and skips permafrost; a band starting at cell 0 is skipped as a "legacy quirk… fixing it changes every map" [OBSERVED, precipitation-generator.ts:205-305; STATED, :225]. Because `prec` is a Uint8Array with unchecked additions, very wet cells can wrap modulo 256 [INFERRED, not test-confirmed]. The wiki calls 100 "pretty wet"/Earth-like and the default winds "already similar to Earth" [STATED, WIKI/Knowledge Base.md:545-553].

**Repack.** Every grid point that is land or coastal water is kept, every fourth deep-coast point and all non-shore lake points are dropped, and midpoints are inserted between coastal neighbours farther apart than the spacing, so the pack is denser exactly along coasts and deep ocean is gone [OBSERVED, pack-generator.ts:16-61; STATED, ARCH generation-pipeline.md:265-266]. Consequences: ocean rings must be built from the grid, a pack cell's climate is its parent grid cell's (`temp[g]`, `prec[g]`) so climate resolution is grid resolution, and coastal midpoint cells duplicate the parent height so coasts are flat shelves in pack heights [INFERRED]. Pack cell ids are therefore not stable across any re-run of regraph, which the docs confirm "invalidates every earlier pack cell index" [STATED, generation-pipeline.md:68].

**Rivers.** The generator (a) tilts a float copy of heights by the distance field so ties resolve coastward, (b) detects closed lakes by BFS from the lowest shore within the elevation limit, (c) resolves depressions with up to 250 iterations of an ε = 0.1 increment relaxation in ascending height order (lake levels raised by 0.2 in the first 85 % of iterations, declared closed after 75 %, abort-and-revert after five iterations without progress, remaining sinks only warn "Edit heightmap to fix"), (d) drains land cells in descending height order by adding `prec[parent]/cellsNumberModifier` and handing flux to the lowest neighbour (haven for coastal cells; the lake's lowest shore cell when the lake's inflow exceeds its evaporation), proclaiming a river when flux ≥ 30, (e) resolves confluences by larger-flux takeover with the loser recorded in `conf`, (f) defines rivers (≥3 cells, source, mouth, parent, basin, widthFactor scaled by cell count, discharge = flux at mouth, `length` in px, mouth width from an empirical power of a px offset labelled "km", sourceWidth from flux), (g) overwrites pack heights with the filled values truncated to Uint8 and downcuts cells ≥ 35 by at most 5 units when erosion is allowed, and (h) inserts 0–2 perpendicular meander points per segment at draw time with amplitude dependent on a phase step that starts at 10 for land sources and 1 for lake outlets [OBSERVED, river-generator.ts:189-595; lakes.ts:47-124; SRC/src/utils/pathUtils.ts:425-487; STATED, docs/prd/meandering-river-routes.md:48-49]. A comment lists real mouth widths from the Amazon to a 40 m stream as the calibration target [STATED, river-generator.ts:629-630]. **No delta, braiding, groundwater, water-table or seasonal concept exists** anywhere in source or docs; a river ends at the first water cell [OBSERVED by grep and at river-generator.ts:308-323]. Navigability is a river cell with flux ≥ 100, and drain resolution walks outlet chains through open lakes to the final ocean or closed lake [OBSERVED, river-generator.ts:10-11, 774-827]. Crucially, **the heightmap editor's "Show drainage" overlay already implements a priority-flood fill (FlatQueue seeded from water and border cells, ε = 1e−4) with single-direction targets and one-pass accumulation, flagging rivers at the same threshold — a D8-style model the generator itself does not use** [OBSERVED, SRC/src/renderers/overlays/drainage.ts:99-164]. The lake level is round2(min shoreline height − 0.1), a fractional value on an integer base; open/closed is decided by the elevation-limit BFS plus a Penman-style evaporation-versus-shoreline-precipitation test; subtypes are frozen (temp < −3), lava (high level, tiny, cell-parity), dry (evaporation > 4×flux with no inlets/outlet), sinkhole, salt (no outlet, evaporation > flux) or freshwater [OBSERVED, lakes.ts:10-16; features-generator.ts:474-486].

**Biomes, ice, decoration.** Thirteen default biomes carry habitability, relief density, a relief pool and a movement cost; the lookup is a 5 moisture × 26 temperature matrix of ids with four overrides (water, permafrost, hot desert, wetland by moisture and altitude), where moisture per pack cell is the mean of own and neighbouring `prec[g]` plus a river bonus; the docs say matrix values are "generator configuration, not map state" [OBSERVED, biomes-generator.ts:19-91, 116-131, 203-219; STATED, ARCH data-model.md:501]. Ice re-seeds Alea, traces glacier isolines at temp ≤ −8 and shrinks 20 % of eligible cold water cells into icebergs [OBSERVED, ice-generator.ts:259-305]. Relief icons are generated on first draw in shuffled cell order by first-matching ordered rules (snowy mountains, mountains, hills by height and temperature) or by biome pool, Poisson-disc sampled inside the cell polygon, **without an Alea re-seed, so placement depends on draw-time PRNG state** [OBSERVED, relief-generator.ts:64-106, 191-274; INFERRED non-reproducibility]. Coastline fractalisation recursively midpoint-displaces each non-border edge up to a default depth of 4 with amplitude ∝ √length × a two-octave position-keyed roughness field, seeded per feature so that "the same map with the same settings always draws the same coast" and edits stay local; cells, areas and ports are untouched [OBSERVED, coastline-generator.ts:464-657; STATED, UPD v1.153.0:37; WIKI/Coastline-Editor.md:117].

**Resample and determinism.** Submap/transform deep-clone grid and pack, generate a **new grid with the same seed**, copy `h/temp/prec` per new point from the nearest parent pack cell by inverse projection, rerun markup/lakes/temperature/pack/markup/ice, then re-attach per-cell data from the nearest parent *land* cell and restore rivers from the parent's meandered points rather than regenerating them, so a submap's rivers can disagree with its re-filled heights; identity is preserved by coordinates, not ids [OBSERVED, SRC/src/generators/resample.ts:26-499; INFERRED]. `Math.random` is Alea(seed) and is re-seeded at setSeed, grid, heightmap, markupGrid, precipitation, rivers, ice and feature naming; everything that changes the option set, the extent, the cell count, the template, the climate anchors, the height exponent, the lake limit, the depression steps or the code changes the map, and the maintainers keep legacy quirks "because fixing it changes every map" [OBSERVED, seed.ts:20 and the eight re-seed sites; STATED, precipitation-generator.ts:225; heightmap-generator.ts:186]. The glossary's "a seed is not an identity: regenerating with the same seed makes a different Map" refers to map identity, not geometry [STATED, SRC/docs/domain/glossary.md:276-277]. Cross-engine determinism is undocumented: fractional `Math.pow` and trig in meanders can differ by an ULP across JS engines, and the PNG path depends on canvas downscaling [INFERRED].

**Stated limitations.** Planar equirectangular model; rivers need every land cell to have a lower neighbour; only mouth width is available; temperature is a world-wide annual mean; lakes can only be created through the heightmap and any heightmap edit regenerates rivers, lakes and biomes even in Risk mode; the data model "is poorly defined, inconsistent and not well-documented"; `pack.cells.prec` is "in unspecified scale"; the Keep/Risk/Resample paths "can silently fall behind when a generation step is added" [STATED, WIKI/Knowledge Base.md:73, 341, 425, 473, 481, 585, 721, 809; ARCH data-model.md:1, 93; generation-pipeline.md:175-178]. Observed but unstated: ε-relaxation produces flat floors and can leave unresolved sinks; ocean heights are not simulated (`t` is a hop count, not bathymetry); winds are axis-aligned marches with no Coriolis; Uint8 precipitation and Uint16 flux can overflow silently; height has no absolute datum [OBSERVED/INFERRED, physical-pipeline notes §4].

## The human and political layers: a one-shot tableau built from two primitives

FMG's human layers are one strictly ordered single pass over the pack: a per-cell suitability score is computed once, and everything else is placed or grown from it with **quadtree-spaced greedy placement** (culture centres, capitals, towns, religion cores, markets) and **cost-limited Dijkstra flood fill** (cultures, states, provinces, religions, markets, several zones) [OBSERVED, human-layers notes §1; generation-pipeline.ts:26-48]. The creator's framing is unambiguous: "The map is static. Over-time simulation is planned, but not yet implemented"; "The Generator doesn't simulate wars"; the economy "is a single calculated cycle, not a running simulation", with ticking, spending, tariffs and a regenerate-production action explicitly out of scope [STATED, WIKI/Knowledge Base.md:465, 661, 761; SRC/docs/prd/state-taxes-and-treasury.md:156-162]. The ordering constraint worth preserving verbatim is suitability → placement → routes → everything that reads connectivity (burg population, inns, brigands, disease zones, journeys all read routes) [OBSERVED, dependency table in human-layers notes §2; INFERRED recommendation].

## Data model, formats, identity and migration: two structure-of-arrays graphs, one positional text file, forward-only gates

FMG keeps a world as `grid` (the jittered source graph: points, boundary, `h` Uint8, `t` Int8, `f` Uint16, `temp` Int8, `prec` Uint8, features) and `pack` (the repacked graph: `p` centres, `g` parent grid id, `h` copy, `area` Uint16, `t`, `f`, `s` Uint16, `pop` Float32, `biome`, `burg`, `culture`, `state`, `province`, `religion`, `r`, `fl` Uint16, `conf` Uint8 at load, `harbor`, `haven`, `good`, `market`, `routes` adjacency) plus ~20 entity arrays [OBSERVED, SRC/src/types/GridGraph.ts:5-24; PackedGraph.ts:22-58; load.ts:341-368; STATED, ARCH data-model.md:7-116]. The inline comments in `PackedGraph.ts` are partly wrong (`g` described as "ground type", `conf` as "water confidence", `p` as "polygon points", `b` typed boolean) and the generator code and data-model.md are authoritative [OBSERVED]. Entity keying is mixed: features, cultures, burgs, states, provinces, religions and biomes are index-keyed with element 0 reserved and `removed` tombstones that never shrink the array (burgs[0] is the number 0, provinces default to `[0]`); rivers, routes, markers, zones, ice, goods, markets, deals, added labels and journeys carry their own `i` (route id 0 is valid; goods ids start at 1); relief icons and measurers have no ids at all [OBSERVED, load.ts:336, 602-607; STATED, data-model.md:124-474]. Definition sets referenced by name (burg groups, label groups, military unit types, transports, custom icons, coastline settings, relief rules) live in `options.map`, not `pack` [STATED, ARCH configuration.md:123-134; OBSERVED, options-schema.ts:156-172].

The unit conversions that give the arrays physical meaning are all late-bound display formulas: height to metres as above; horizontal scale "1 map pixel = N units" with default 3 and range 0.01–20, unit-agnostic (so the default 1280×800 map is 3,840 × 2,400 km); area = px² × scale²; people = rural points × scale + urban points × scale × urbanization rate; river `discharge` is the unconverted flux at the mouth labelled m³/s, river `width` is an empirical power of a px offset labelled km, and river `length` sums pixel distances although data-model.md calls it km [OBSERVED, unitUtils.ts:59-105, 183-187, 228-232; river-generator.ts:356, 559-561, 624-633; STATED, data-model.md:289-291; WIKI/Scale-and-distance.md:17-71].

**The `.map` container** is plain text: 53 CRLF-separated positional fields whose header is `version|license|date|seed|width|height|mapId`, field 1 the whole `options.map` JSON, field 5 the serialised SVG, fields 6–11 the grid, 12–15 features/cultures/states/burgs, 16–27 typed pack arrays joined by comma, and then religions, provinces, name bases (default-identical bases omitted), rivers, fonts, markers, cell routes, routes, zones, ice, goods, markets, deals, measurers, added labels, the styles record (48), relief (49), layer state (50), graph overrides (51) and journeys (52), with four deprecated empty slots [OBSERVED, SRC/src/services/io/save.ts:139-193; load.ts:306-368]. Pack geometry (`p/c/v`, vertices) and `cells.g` are **not saved**; they are rebuilt at load by re-running `Grid.rebuildGraph`, `Pack.generate` and `Features.markupPack`, so the stored per-cell arrays are only meaningful if `Pack.generate` is bit-for-bit stable across versions, which the repo does not document for Delaunator versions [OBSERVED, load.ts:302-312; INFERRED]. Gzip and base64 variants are accepted on read; there is no gzip writer [OBSERVED, load.ts:172-218]. The `.map` format is declared the project's "public API" under semver (major = breaks maps, minor = needs auto-update, patch = no change) [STATED, SRC/src/services/versioning.ts:1-15], and the invariant is that "Saving a `.map` file MUST preserve the exact world state so it can be reloaded identically" [STATED, SRC/CONTEXT.md:69]. The creator nonetheless calls the format "a stack of accidents" and the backlog issue #1698 proposes replacing the delimited format with JSON, MessagePack or Protocol Buffers [STATED, UPD v1.149.0:72; https://github.com/Azgaar/Fantasy-Map-Generator/issues/1698].

**Migration** is a single ordered function walking ~55 `isOlderThan` gates from 1.0.0 to 1.154.1, run after parse and SVG insertion; a pre-step converts the pre-1.152 pipe-delimited settings string into the settings object and infers the requested cell count from the stored spacing; the 1.139 biomes step is hoisted first "because older migrations consume biome data"; files newer than the app are refused [OBSERVED, AU:94-131, 2214-2391; load.ts:153-166]. Many gates manipulate the SVG DOM or call generators (1.0 regenerates religions; 1.99 reconstructs routes from SVG paths; 1.140 rebuilds label groups from the SVG with zoom extents derived from the legacy font-size formula; 1.146 recovers moved vertices from the SVG if under 5 % are unresolved; 1.150 harvests styles from the SVG) [SHOWN, AU:133-137, 941-1004, 1287-1526, 1645-1838]. Load-time integrity repairs reset dangling references to 0, re-find burg cells from x,y, dedupe marker ids and drop dangling route links; the culture branch zeroes `cells.province`, apparently a bug [OBSERVED, load.ts:414-650]. Migrations must carry their own copy of the old world and never lean on the live schema; validation repairs rather than rejects [STATED, ARCH configuration.md:214-246].

**Identity** is positional for political entities and absent for decoration; a map's identity is its creation timestamp in the header; locked burgs **are assigned new ids on regeneration** with their state's capital and market references re-pointed; graph overrides are kept as `[original, edited]` vertex pairs and restored only if the rebuilt vertex still has the original coordinate [OBSERVED, save.ts:64; burgs-generator.ts:842-862; graph-override.ts:42-57]. Stable cross-session addressing in FMG therefore reduces to (creation timestamp, entity kind, id as of that save) plus grid cell id for cell-level facts, never pack cell id [INFERRED].

**Exports** are SVG (clone with fonts, patterns and icons embedded and Inkscape rewrites), PNG/JPEG at a chosen resolution, zipped PNG tiles, GeoJSON for cells (polygon per pack cell with id, unit-converted height, biome, feature type, people, state/province/culture/religion ids and neighbours in equirectangular lon/lat; the wiki admits "gaps or overlaps"), routes, rivers (meandered points), markers and zones; JSON Full/Minimal/PackCells/GridCells (Full includes `g`, `p`, `v`, `c`, vertices, all entities, grid cells with heights/temp/prec and points); CSVs from every overview; a 3D OBJ; emblem images; an icons zip; a style preset; and a share URL of seed + width + height [OBSERVED, SRC/src/services/io/export.ts:65-978; export-json.ts:36-240; STATED, WIKI/GIS-data-export.md:30-46]. Imports are `.map/.gz` (file, `maplink` URL, Dropbox, IndexedDB), images as heightmaps by palette quantisation, precreated PNGs, template text, name bases, notes/burg-name/culture CSVs, style presets, icon archives, pictures, fonts, Armoria COAs and overlay images; **there is no GeoJSON, shapefile or DEM import, no print/PDF export and no VTT export** [OBSERVED absence, grep over `SRC/src/services/io/`]. URL parameters let a host open a hosted `.map`, generate from `seed` + `width` + `height` + `options=default` (reproducible only on the same generator version), pick a layer preset, focus a cell or burg, and accept the MFCG back-link; no URL parameter sets template, culture set or density [OBSERVED, SRC/src/services/url-params.ts:16-182; STATED, WIKI/URL-parameters.md:4-23; INFERRED gap]. The future model is one JSON `map` object with `meta`, `facts` (= `options.map`), `layers`, `style` and `data`, with entity collections keyed by id as object maps [STATED, ARCH future-data-model.md:1-204].

## Editing, regeneration and model drift: a clean edit API undone by hand-listed redraws and no global undo

FMG 2.x is a four-layer app: typed-array world state plus a `styles` record → generator model classes that own every mutation and expose public edit methods (`Burgs.rename`, `States.setCells`, `Labels.setLayout` …) validated in `model-edits.test.ts` → ~60 lazily-loaded controllers → idempotent `draw-*` renderers coordinated by a `Layers` registry [OBSERVED, ARCH architecture.md L186-188, L403-404, L530-548; SRC/src/generators/model-edits.test.ts]. A minority of controllers still mutate `pack` directly (colours, zone cells, river control points, relief icon positions, goods cell assignment, diplomacy) [OBSERVED, editing notes §2 table]. **There is no global undo**: only the heightmap editor (100 snapshots), paint editor (100 strokes), wrap tool (1,000 strokes), diplomacy brush, notes, template editor and transform keep session-scoped histories, and Ctrl+Z works only inside tools that render undo buttons [OBSERVED, heightmap-editor.ts L57; paint-editor.ts L59-60; wrap-tool.ts L116; diplomacy-editor.ts L208; hotkeys.ts L55-56; STATED, WIKI/Knowledge Base.md L51-53]. The one real transaction is the Assistant's proposal: operations are tried on a structured-clone draft world, changed rows are recorded before/after, Apply/Undo/Redo check that the live world still matches, and reference integrity is verified; the Assistant refuses to propose the relief-regenerate effect because Undo cannot restore it [OBSERVED, SRC/src/controllers/assistant/proposals.ts L21-87; redraw.ts L7-60; operations.ts L24-47]. The heightmap editor has three apply modes: Erase clears all human layers and runs the ErasePipeline; Keep copies heights into pack via `cells.g` and cannot change the coastline; Risk re-runs markup/lakes/climate/regraph, re-attaches per-cell arrays by grid index, forces burg cells to land and relocates burgs by nearest land [OBSERVED, heightmap-editor.ts L525-547, L624-654, L711-737; STATED, ARCH generation-pipeline.md L155-191]. Regeneration is a menu of per-domain commands, each running one generator's `regenerate`, honouring per-entity `lock` (sometimes by re-indexing), then redrawing a hard-coded layer list; nothing downstream is invalidated automatically [OBSERVED, SRC/src/components/map-commands.ts L669-825; states-generator.ts L204-258; burgs-generator.ts L830-870]. A seed reproduces only a fresh generation; user edits are absorbed into data, not kept as a replayable log [STATED, WIKI/Quick-Start.md L65; Knowledge Base.md L919-921; INFERRED].

The researchers' consolidated **model-drift list** — places where FMG lets the map disagree with its own model — is the clearest negative specification for PLAT's derived-state discipline:

## Rendering and styles: 42 SVG layers, a viewport reconciler, and a style store that finally left the DOM

One SVG holds a `Layers` registry of 42 layers whose registration order is z-order; each has an idempotent `draw` that reads only state; `restore` never draws; visibility and order are saved in `.map` field 50; 13 layer presets exist with custom ones in localStorage [OBSERVED, SRC/src/components/layers.ts L41-407; layers-presets.ts L7-44; save.ts L76, L190; STATED, docs/prd/layers-management.md]. A `ViewportRenderer` reconciles heavy layers (labels, markers, burg icons, emblems, relief, goods, rivers, routes) against the visible bounds with 80 px overscan and a 40 px guard, which the creator describes as "the difference between a few hundred DOM nodes and several thousand" [OBSERVED, SRC/src/renderers/viewport/viewport-renderer.ts L139-182; STATED, UPD v1.149.0:23]. Zoom extent is [1,20]; font sizes follow zoom curves and halo stroke widths scale by scale^0.8; performance presets (quality/balance/speed) trade shape rendering, state halos and viewport-redraw mode [OBSERVED, zoom.ts L8-110; performance.ts L9-13]. Styles are a zod-validated record keyed by element with `attrs`/`options`/`groups`, stored in `.map` field 48, with 15 system presets, a schema-driven editor whose controls come "from the same definitions used to store and validate the map's style", declared effects (write attribute, zoom, regenerate relief, draw) and a baseline diff/reset; "On load, an older map's styling is read out of its SVG" [OBSERVED, ARCH style.md L72-373; style-editor/effects.ts L14-26; STATED, UPD v1.150.0:103-109; v1.154.0:41-53]. Labels are entity-derived records with per-label overrides (`pathPoints` undefined = auto, empty = plain text, non-empty = own path), state labels fitted by a raycast at 9° steps with font bounds 40–160 %, 14 default groups with zoom bounds, and a spread solver (12 directions × 6 steps, simulated annealing 2k–20k iterations) whose results are written as overrides and never re-run [OBSERVED, labels-renderer.ts L13-125; label-data.ts L50-168; fit-state-label.ts L8-80; label-raycast.ts L29-109; label-spread.ts L92-129]. Icons are sets with glyph ids, relief descriptors with alias fallback, custom icons in IndexedDB and a single picker for all slots [OBSERVED, ARCH icons.md; docs/prd/icon-library.md, icon-assets.md, relief-icon-pools.md]. The creator's 2024 position was that "Graphics is slow, but it's SVG so there is no room for improvement here" with generation itself at ~0.3 s on default settings, and the architecture doc keeps WebGL as an "alternative renderer" option; a `relief-webgl-renderer` branch exists [STATED, https://github.com/Azgaar/Fantasy-Map-Generator/discussions/1126; ARCH architecture.md:5-17; SHOWN, remote branch list]. The 3D view is presentation-only (mesh, globe, eroded bake, satellite texture) and "cannot be used for editing" [STATED, SRC/docs/domain/3d-view.md:1-25]. Mobile is "not supported" [STATED, WIKI/Q&A.md:60-61]. The benchmark harness records six totals over three rounds and flags >10 % median changes but publishes no absolute timings [STATED, ARCH benchmark.md:17-67].

## Roadmap, community and ecosystem: an active, PRD-driven project whose users most want history simulation and scale

FMG is not a stalled hobby tool. As of 2026-10-16 the repository shows 6.1k stars, ~1.0k forks, 130 watchers, 2,594 commits, 1,061 issues (47 open, 1,014 closed) and 4 open PRs, with v1.154.2 released the same day and desktop installers attached [OBSERVED, GitHub search API and https://github.com/Azgaar/Fantasy-Map-Generator fetched 2026-10-16]. The 2026 release cadence runs 1.119 Jagged Coastlines (26 Apr), 1.123 Eroded Terrain (12 Jun), 1.124 Economy (17 Jun), 1.140 Labels (12 Aug), 1.149.1 Electron (27 Aug), 1.150 Journeys (1 Sep), 1.153 Omnibar (16 Sep), 1.154 Icon Library (5 Oct), 1.154.2 (16 Oct) [STATED, releases page]. "FMG 2.0" is an architecture, not a product: the goals are responsiveness at 100k cells, bounded memory, generation separated from rendering, world data independent of the DOM, gradual JS→TS "without breaking existing `.map` files" and room for alternative renderers; the refactor "is explicitly incremental… too large for a full rewrite" [STATED, ARCH architecture.md:5-17, 778-786]. The wrap-tool PRD records that a general deformation tool "is shelved" because geometry and entity coordinates live in separate representations [STATED, docs/prd/wrap-tool.md:19-23]. Remote branches suggest experiments in `relief-webgl-renderer`, `cylinder-wrap`, `raster-layer`, `alternative-grids`, `dev-economics` and `translation` [SHOWN, git branch listing]. "None of this has a release date" [STATED, UPD v1.149.0:106; v1.153.0:158].

## The SettlementForge host integration: a geography-only iframe, an opaque blob, and a frozen digest that no settlement input reads

**The fork.** SettlementForge vendors upstream's Vite build output at **v1.114.2** (upstream bump `bb5039d7`, 2026-04-09; next bump 2026-04-20), identified by `VERSION` in `public/map/versioning.js:19`, corroborated by the TinyMCE subtree entering the repo on 24 April 2026 and the `sfdrop16` revision tag; it therefore predates the minimap, Fill brush, jagged coastlines, eroded terrain, the economy, journeys, the declared pipeline, the styles store and every data-model migration after 1.113 [OBSERVED, HOST/public/map/versioning.js:19; HOST/THIRD-PARTY-NOTICES.md §1.4; HOST/src/lib/mapRuntimeConfig.js:20; upstream git log -S; CL:124-135]. Host modifications are (a) two new files, `sf-origin.js` (single trusted parent origin, loopback fallback) and `sf-bridge.js` (1,728 lines: the whole RPC surface; `randomizeOptions` wrapped to force a curated template and zero `statesNumber`, `manorsInput/Output`, `religionsNumber`, `provincesRatio`; canvas sized to the iframe; injected CSS hiding burgs, labels, routes, borders, markers, zones, armies, emblems, rulers and all chrome; a custom `sfArchipelago` template at probability 0); (b) ~160 lines of inline `main.js` patches (logging gated, service worker removed, trusted `maplink` check, generate-on-load bail when `pack` is empty, OpenWidget chat disabled, a ~70-line drag-drop block minting `sf_<id>_<time>` burg ids and posting `fmg:settlementPlaced`); (c) escaping and small bug fixes across ~30 `modules/**` files; (d) rebranding, 234 of 338 charges removed as non-CC0, 23 textures replaced by two estate tiles, GTM/analytics removed, `sw.js` deleted; and (e) **a rebuilt bundle `index-Bp79q281.js` that exports `window.Settlements` instead of `window.Burgs`**, with 28 `Settlements.*` call sites across the fork [OBSERVED, HOST/public/map/sf-origin.js:1-77; sf-bridge.js:83-208; main.js:8-687; bundle grep; STATED, HOST/docs/fmg-fork.md:28, 150-188]. That rename proves the bundle was rebuilt from a **modified copy of upstream's TypeScript source that is not in the clone** (no build script, no generator source outside the bundle), which contradicts `docs/fmg-fork.md:81-84` ("FMG-native (no SF markers)… not diffed against upstream") and means the runbook's upgrade step ("regenerate from the new release's build") would drop the rename and break every `Settlements.*` call; the bundle is also not hash-pinned and `main.js` is "outside all gates, reconciled by hand" [INFERRED from OBSERVED; STATED, HOST/docs/fmg-fork.md:84; HOST/ARCHITECTURE.md:446-447]. A known upstream typed-array indexing bug in deep-depression lakes is deliberately left unfixed to preserve same-seed output [STATED, HOST/docs/fmg-fork.md:33]. The host's decision of 2026-05 was "no hard fork" because "we own ~14,000 lines of map-generation code we don't understand", while ASSESSMENT.md lists the fork as an open structural risk: "Either commit to hard-fork or upstream the bridge hooks" [STATED, HOST/docs/fmg-fork.md:104-130; HOST/ASSESSMENT.md:10, 35].

**The bridge.** A request-id-correlated `postMessage` RPC: the parent sends `settlementEngine:*` with `_rid`, the child replies `fmg:*Reply` or `_error`, push events carry no `_rid`, and both ends validate `event.origin` and `event.source` against an explicit target origin with a 15 s load watchdog [OBSERVED, HOST/src/lib/mapBridge.js:28-213; sf-bridge.js:1646-1668; useMapBridge.js:92-217]. Commands cover `requestBurgList`, `placeSettlement` (screen→map via the viewbox CTM, `findCell`, mint an id; **does not add a burg**), `removePlacement`, `clearAllPlacements`, `restorePlacements` (a no-op echo), `computeRoadNetwork` (an A* over `pack.cells` with biome/elevation/river/corridor-reuse costs, sea bias 1.15, 25,000-iteration cap, batch-order dependent), `getSpatialPack` (copies `cells.h, biome, r, p, c, fl, g` and `grid.temp, grid.prec`), `exportThumb`, viewport get/set/fit, `saveSnapshot`/`loadSnapshot` (`prepareMapData`/`uploadMap`), `resetMap(seed)`, `activateTool` (heightmap/rivers/coastline/lakes/biomes editors; `terrainChanged` fires **on activation only**), undo/redo, `setFmgLayer` and `setTemplate` [OBSERVED, sf-bridge.js:292-1642; HOST/src/store/mapSlice.js:230-245]. Push events `fmg:burgList`, `fmg:mapReset`, `fmg:snapshotLoaded` and `fmg:placementsRestored` have **no host listener** [OBSERVED, grep of `.on(` sites]. ## Import-adapter field mapping

The adapter's job is to read an existing FMG world (the host's stored 1.114.2 snapshots and users' `.map`/Full-JSON files) into PLAT's native model: a raster heightfield in integer centimetres against one datum, explicit water-surface records, a flow/accumulation raster, a routes graph and host-owned political facts. Classes: IMPORT-DIRECT (copy with unit conversion), IMPORT-DERIVE (recompute from FMG inputs), IMPORT-DROP (reason), NOT-APPLICABLE. The recommended canonical input is FMG's **JSON Full export**, because it carries `g`, `p`, `v`, `c`, vertices, all entities, grid heights/temp/prec and points, and is versioned by `info.version`; the `.map` path requires rebuilding pack geometry (Delaunator plus the same boundary clipping and `Pack.generate` filtering) because neither pack geometry nor `cells.g` is saved, and FMG's migrations cannot run headless because they manipulate the SVG DOM and call generators [OBSERVED, export-json.ts:124-199; save.ts:139-193; AU:133-137; INFERRED]. The host's current capture (`h, biome, r, p, c, fl, g` + grid `temp, prec`) is a strict subset of this mapping and omits the fields the host already wishes it had [OBSERVED, HOST/public/map/sf-bridge.js:1303-1324; waterBodies.js:1-60].

## Conclusion

The most useful thing FMG offers SettlementForge is not its code but the shape of its mistakes and the order in which its author corrected them. Every subsystem that FMG moved out of the SVG between 2021 and 2026 — rivers, rulers, markers, routes, zones, ice, labels, measurers, biomes, relief, styles, layer state, notes — was moved because the drawing had been the database, and every one of those moves required a migration that reads the old drawing back heuristically. FMG's physical model, meanwhile, was never upgraded past its 2017 shape: the drainage overlay in the heightmap editor is now a better hydrology model than the generator it previews, and the creator's own PRD folder contains no plan to change that. A native PLAT engine that starts from canonical typed data, an explicit datum, a priority-flood D8 raster and persistent addresses therefore inherits FMG's hard-won *contracts* (what a lake is, what a port is, when a river is navigable, how a route network should be built, how labels and styles should be stored, how an edit should be transacted) without inheriting the decade of drift that FMG is still paying down.

For the host the implication is sharper than "replace the iframe". SettlementForge already treats the dossier as the only truth and already measures the map against it after the fact; it already selects road edges host-side, already freezes an integer digest, already ports FMG's cost law into its own code, and already refuses to invent a coordinate frame it cannot verify. Those are the behaviours of a system that wants a one-way host→map contract and has been prevented from having one only by an opaque, browser-bound, version-pinned generator whose rebuilt bundle has no source in the repository. The native generator's first deliverable should be the boundary-condition charter the audit found missing — frame in integer centimetres, datum, sea edges, river requirements, biome and climate vocabulary — because that charter, not the terrain algorithm, is what turns the realm map from an illustration that is later measured into an input that is honoured.
