## 0. What "the dossier" is

- CONFIRMED (settlement.schema.js header, normalizeSettlement.js, assembleSettlement.js): the dossier is ONE plain JSON object per settlement — "the settlement" — produced by `generateSettlementPipeline(config, importedNeighbour, { seed, customContent })`. The pipeline's last step (`assembleSettlement`) builds a FLAT object (the "legacy shape"), then passes it through `normalizeSettlement` (version stamps, a stable settlement `id`, default containers, schema migrations) and then `promoteStressorsToConditions` + `reapplyEventConditions`. The richer nested `CanonicalSettlement` typedef (`identity`, `geography`, …) is a declared FUTURE target; today nothing restructures into it ("purely additive").
- CONFIRMED: a freshly generated dossier has exactly 37 top-level keys (all three generated tiers): `name, tier, population, institutions, structuralViolations, structuralSuggestions, neighborRelationship, economicState, spatialLayout, availableServices, powerStructure, settlementReason, npcs, relationships, factions, conflicts, resourceAnalysis, economicViability, history, stress, stressors, config, _config, pressureSentence, arrivalScene, defenseProfile, prominentRelationship, coherenceNotes, simulationTrace, _seed, simulationVersion, generatorVersion, id, activeConditions, aiOverlays, userCanon, schemaVersion`.
- Three LAYERS must be kept apart (CONFIRMED from the schema file and the domain modules read):
  1. **Stored generation output** — the 37 keys above. Sizes observed: hamlet 75 KB, town 191 KB, city 249 KB of JSON.
  2. **Stored campaign/lived additions** — fields a canonized settlement gains from events and the world pulse (`eventLog`, `_userEdits` on entities, `neighbourNetwork`, `tierHistory`, `populationHistory`, `primaryDeity`, impairments/status on entities, `updatedByPulse` faction state, …) and campaign-level state OUTSIDE the settlement object (`worldState`, the realm map's `mapState.placements`, the frozen spatial digest). See §10 and §12.
  3. **Derived read-models (NOT stored)** — computed on read by pure `derive*` functions: faction profiles (`faction.<snake>` ids), NPC profiles, supply-chain states (`chain.<need>.<inner>`), threat profiles, district profiles (`district.<snake>`), causal state (14 substrate variables), capacities, daily life, history beats, map profile, regional graph, the AI grounding envelope. `docs/settlement-schema.md` calls these "Derivation outputs (live, not stored)".
- CONFIRMED (fieldManifest.js): SF keeps a "frozen-vs-live" manifest: some generation-written fields are `live` (the world pulse keeps them true each tick: `population`, `tier`, `economicState.foodSecurity.{storageMonths,resilienceScore,deficitPct,surplusPct}`, `defenseProfile.scores.disaster`, per-faction live state on `powerStructure.factions[]` with `updatedByPulse`, `neighbourNetwork[].relationshipType`, `regionalGraph.edges[].relationshipType`), others are `snapshot` (a generation verdict never refreshed: `defenseProfile.scores.{military,internal,monster,economic,magical}`, `foodSecurity.{dailyNeed,dailyProduction}`, `foodSecurity.magicTradeChannel`). For the map this is the list of dossier fields that can change without any authored event.
- CONFIRMED (canonicalAccessors.js): exactly three alias resolvers exist — `canonStressors` (stressors ← stress ← stresses), `canonExports` (economicState.primaryExports ← exports), `canonImports` (primaryImports ← imports). `FIELD_ALIASES` in the schema holds only `stressors: ['stress','stresses']`.

- **(branch) deltas, CONFIRMED on `fp/integration-2026-09-23` outputs and source:** a generated dossier has **41** top-level keys — the 37 above plus `isolationSupport`, `culturalIdentity`, `culturalNotes`, `generationCoherenceReceipt`; sizes hamlet 85 KB, village (stressed) 143 KB, town 204 KB, city 256 KB, metropolis 277 KB, town-with-neighbour 308 KB. The pipeline steps are `resolveConfig, buildGenerationContext, resolveResources, resolveStress, resolveNeighbour, assembleInstitutions, subsumptionPass, cascadePass, isolationPass, stressConfirmPass, generateEconomy, generatePower, powerEconomyReconcilePass, neighbourFactions, factionCorrelationPass, economyReconcilePass, structuralValidationPass, generatePopulation, corruptionPass, coherenceRepairPass, generateNarratives, assembleSettlement` (no `seedStartingPantheon` — generation no longer bakes a latent pantheon; see §9). `fieldManifest.js` adds live `economicState.treasury.coin` (absolute integer state coin, written by `worldPulse/treasury.js#advanceTreasury`, absent at generation) and snapshot rows for `economicViability`, `structuralViolations`, `structuralSuggestions`, `coherenceNotes`, `defenseProfile.magicDependency`. ## 1. Identity and keys — how each record is keyed, and whether the key survives

CONFIRMED by reading `normalizeSettlement.js`, `lib/entities.js` (`idOf`, `factionIdFromName`), `dossier/entityLinks.js` (`buildDossierEntityIndex`), `npcGenerator.js:1729-1732`, `factionRoles.js:140`, `events/mutateEntities.js:228,375`, `worldPulse/{institutionLifecycle,entrepotKernel,calamityKernel,successorNpc}.js`, and by inspecting the three generated dossiers:

| Record | Key as stored | Key as derived | Stable? |
|---|---|---|---|
| Settlement | `id` = `s_` + 16 hex, FNV-1a hash of `_seed` (else a content hash of name/tier/population/collection counts) | — | Stable across reload and across a same-seed regeneration; a new seed = a new id. The canonical typedef says "preserved across regenerations and saves". |
| NPC (generated) | `id` = `npc_1…npc_N`, assigned in generation order after role selection | `npc_N` | Stable across reload and edits; NOT stable across a regeneration or an NPC reroll (`regenNPCsPipeline` renumbers). |
| NPC (structural, from faction roles) | `npc.<faction>_<role>_<i>` | same | Stable while the faction name holds. |
| NPC (successor from the pulse) | `npc.successor_<num>` | same | Stable once minted. |
| Institution (generated) | NO `id` field at all (0 of 18 / 51 / 50 in the three dossiers); `catalogId` (e.g. `city_granaries`) on catalog-drawn ones (15/18, 45/51, 43/50); cascade-added ones have neither | `institution.<snake name>` (`idOf`), the dossier index uses the hyphen slug of the name | Name-derived: survives reload; changes if the name changes; `catalogId` is a KIND key, not an instance key (no duplicates observed within one dossier). Custom institutions carry `localUid` (the custom registry's uid). |
| Institution (added by an event or the pulse) | `id` = `institution.<slug name>` | same | Stable once minted (name-derived at mint time). |
| Power faction (`powerStructure.factions[]`) | NO `id`; keyed by its `faction` NAME string | `faction.<snake name>` (`factionIdFromName`); an optional rename-decoupled `faction.id` is honoured as an alias when present | Name-derived. Event-added factions get `id: faction.<slug>`. |
| NPC social faction (`factions[]`, top level) | NO id; `name` | — | Name only. |
| Relationship (NPC↔NPC) | NO id; `npc1Id`/`npc2Id` pair + `archetypeKey` | — | Pair key only. |
| Quarter (`spatialLayout.quarters[]`) | NO id; `name` | `district.<snake name>` | Name-derived; the quarter list is recomputed from institution names at generation. |
| Supply chain (`economicState.activeChains[]`) | `needKey` + `chainId` (catalog keys, e.g. `trade_entrepot` / `transit_finance`) | `chain.<need>.<inner>` | Catalog keys: stable as long as the chain exists. |
| Active condition | `id` = `condition.<archetype>.<suffix>` | same | Stable once stored. |
| Historical event | usually no id; `name` | `event.<slug name>` or `event.index-N` | Name/index-derived. |
| Neighbour link (`neighbourNetwork[]`) | persisted `id` (`link_*`, `generated_*`, `live_*`) | `neighbour.<slug name>` fallback | Stable when persisted. |
| Deity | `_deityRef` (e.g. `deity:core:brannor`) inside `config.latentPantheon` | `deity.<slug name>` | The `_deityRef` is a real catalog reference key. |
| Trace entries | `targetType` + `targetId` using the `institution.<snake>` / `tier.<tier>` convention | — | — |

All CONFIRMED from the generated dossiers and `src/data/constants.js` unless marked.

- **Config.** `config` = the RESOLVED inputs (23 keys in the city: `settType, culture, terrain, terrainType, terrainOverride, tradeRouteAccess, monsterThreat, magicLevel, tier, priorityEconomy/Military/Religion/Criminal/Magic` (0–100, default 50), `nearbyResources[]`, `nearbyResourcesDepleted[]`, `nearbyResourcesCustom[]`, `stressType, stressTypes[], intendedStressTypes[]`, `_population`, `faith`, `latentPantheon`); `_config` = the RAW user inputs with sentinels (`'random'`) intact — the regeneration input.
