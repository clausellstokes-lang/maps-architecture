# JUDGE — Improvement realism and restraint (lane `design/judge-improvement`)

Fable judgment seat, 2026-09-25. STATUS: COMPLETE (LANDED 2026-09-25) — written incrementally; §0 records what was read; the verdict
is in §6, the grafts in §7, the gaps no proposal fills in §8, judgment calls and CONFIRMED-vs-PLAUSIBLE in §9.

Lens: **IMPROVEMENT REALISM AND RESTRAINT.** For every BASE must-have and should-have in `docs/IMPROVEMENTS.md` §5
(and its hooks §5.4 and stage-2 readiness §5.5), each proposal is asked three questions — (1) is the mechanism real
(would it work as written, or is it a feature line?), (2) is the acceptance metric measurable (a number or a test that
can run against B-CITY / B-EDIT / B-FUZZ / B-REF / B-ZOOM, not "better"), (3) does it sacrifice anything the references
get right (`docs/IMPROVEMENTS.md` §4 R1–R16 and each opportunity's restraint clause)? Feature-listing without a
mechanism and "better" without a number are scored down; an "improvement" that loses legibility, sub-second speed,
charm or one-click simplicity is scored as a regression, not a gain. Parity is the floor; the owner's tiebreaker
(constraints and precision over the prettier or simpler approach, legibility and one-click as a floor) is applied where
MFCG-style and FTG-style mechanisms conflict.

## §1 The rubric this seat holds the proposals to

Derived from `docs/IMPROVEMENTS.md` §5 (the split the architects are held to). The §5 rule: "for every MUST-HAVE the
architecture must name a mechanism that would work (not a feature line) and adopt the opportunity's acceptance criteria
into its improvement matrix; a must-have without a mechanism, or with a criterion it cannot run against B-CITY / B-EDIT
/ B-FUZZ / B-REF / B-ZOOM, is a validation failure. Should-haves need a mechanism and a place in the build plan; later
items need only the hooks in §5.4."

**Must-haves (17):** O2 deterministic recipe; O6 metres/tables/statistics; O3 robust kernel with typed fallbacks and
no whole-map restarts; O11 schema + registry + API; O1 terrain and hydrology first; O4 two-tier street network (the
fusion core, guarded by criterion (f): network + infill ≤ 100 ms at CITY, block/junction statistics within NG bands);
O5 frontage-first plots; O18 prosperity field + one granularity law; O17 plot model + site plans + heights; O7
content-first land use with context vector and bounded reconcile; O19 greenery by rule; O8 fortification network; O12
display list with LOD, ink default, lit preset, layers, shadow hook; O9 persistent document with scoped regeneration
and undo; O16-core report + honest actions; O13-core curved labels + original grammar; O14-core hinterland + margin.

**Should-haves (9):** O10 intent/character/constraint layers + forms catalogue + placement solver; O13 full; O14 full;
O16 full (thumbnails, drafts, responsive); O12 extras (relief, tiles, low-end tier); O7 simulation module; O11 extras
(VTT, binary, 3-D, GIS-validated GeoJSON); O9 upgrade replay; O2/O6 golden seeds and calibration interface.

**Hooks (§5.4, 8):** ids + sub-seeds; lifecycle + incremental pipeline + conversions; assignment input + placement
solver interface; per-plot context vector + rules as data; building-generator interface with LOD and heights + shadow
hook; layers + drainage + boundary-polygon neighbourhood generator + island outlines; editable versioned tables with
provenance; time-varying circumstances + stored editable prosperity field.

**Keep-tests (§4 R1–R16):** R1 one click, sub-second; R2 legibility first; R3 organic fabric (K1/K2, 4-way 0–15 %);
R4 continuous streetwall + zonal gradient; R5 variety around the mean, mixed use; R6 walls/towers/castle silhouette on
by default; R7 every building a purpose; R8 broad strokes + fine control, fast path never pays; R9 determinism; R10
real units + furniture; R11 water and terrain as one picture; R12 repair over rejection; R13 style as data; R14 storage
economy and tiers; R15 small control surface; R16 names conditioned on features. Plus the "deliberately NOT proposed"
list (no oblique default, no correct hips by default, no RIGID grid default, no always-on labels/shadows, no
meander/erosion simulation, no heavy GPU pipeline for its own sake, no questionnaire, no single-use zoning, no forced
simulation in the one-click path, no hard-coded culture).

**Scoring method (0–100 on this lens).** Three sub-scores, weighted: mechanism reality 40, metric measurability 30,
restraint (nothing the references get right is lost; improvements are guarded by keep-tests) 30. Within each, every
must-have counts 2 and every should-have 1; hooks count as a single 2-point item; a fatal flaw (a must-have with no
mechanism, a regression against §4 that the proposal does not notice, or a metric that cannot run) is deducted
explicitly and listed. Scores are this seat's judgment (PLAUSIBLE); the itemised reasons cite the proposal section
they rest on so they can be checked.
