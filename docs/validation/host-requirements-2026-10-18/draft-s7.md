## Data contracts: receipts, exported functions, snapshots and the no-invented-fact rule

The map draws only what SettlementForge stores, what SettlementForge's own law works out and sends, what the map places on its geometry, or what the owner ruled; nothing is invented (docs/volumes/V13-world.md §5.8 (4), line 3154). A "lens" is one drawn layer over one simulated system, such as plague or territory (V13 §5.8, line 3105). Every mark on a lens is one of four classes, and the map refuses any other:

1. **Host-stored** — a fact the host keeps, drawn exactly as kept (V13 §5.8 (4)(a), line 3154).
2. **Host-derived** — a value the host computes by its own law and sends, labelled "by the host's law" (V13 §5.8 (4)(b), line 3155).
3. **Placement** — the map's geometry used only to put a host fact somewhere, marked `placed` where it is a guess (V13 §5.8 (4)(c), line 3158).
4. **Owner-ruled map derivation** — the territory projection (the "sway") and the patrol cadence, labelled "projection", reaching the host only as offers (V13 §5.8 (4)(d), line 3160).

A world site the DM placed by hand is the map's own fact, class `dmPlaced` (V13 §5.8 (4), line 3161). Anything else is refused with a reason, `refuse.lens.invented` (V13 §5.8 (4), line 3162).

The map does not call host functions; the host runs its own law on the same window and sends the result, labelled "by the host's law" (V13 §5.8 (4)(b), line 3155). ### History and the time scrub: why the map keeps its own snapshots

Every simulated system keeps its facts per settlement or per pair, and the host keeps no history of most of them: bands, shares, phases, axes, stocks, front states (V13 §5.8 preamble, line 3107; lens-implications.md §4.6, line 479). So the time scrub — dragging the view back through past weeks — would have nothing to show but the present. The map therefore keeps the history it scrubs itself (V13 §5.8 preamble, line 3114).

The scrub reads, in order: host-dated facts; the sway's own revision history; the map's snapshots; and, before the first snapshot, the host's own pulse records (V13 §5.8 (8), line 3188). A "plate" is one snapshot per host advance, written when a lens window arrives: the window's facts for both audiences plus the polity facts' seat rungs, stored as deltas against the previous plate with a whole plate every `plates.keyEvery` (V13 §5.8 (8), lines 3193–3196). Plates keep full resolution for 520 weeks behind the present; older plates thin to one per 13 weeks, the last of each host quarter kept; a plate the DM pins with `pinPlate` is never thinned (V13 §5.8 (8), lines 3197–3200).

The plates live in `Document.lensPlates`, outside the model digest, the records digest, the canon and every export, kept across loads with their own storage budget (`WORLD-14`; V13 §2.7, lines 1279–1281; V13 §5.8 (8), line 3195). They are a cache: dropping them loses only the scrub's past (V13 §5.8 (8), line 3205). The map writes them; the host never reads them.

Before the map's first plate, the scrub reads the host's own per-advance pulse records, sent once when the map first binds (`LensFacts.pulses`): their population deltas and outcome severities, at most 80 advances, labelled with their horizon (V13 §5.8 (8), lines 3191–3193; V13 §8.5 row H23, line 3748). The host's horizons are 80 pulse records with interior weeks dropped, 240 news items and 12 population rows (lens-implications.md §4.6, line 489). The older note adds that population deltas are arrays, and that the host's own track reads them as a map and probably never fires (lens-implications.md §4.6, line 484).

The territory and patrols lenses scrub from the sway's own revision log, on its own version axis (`swayRevision` with the polity law's version), never the canon's and never a geometry change (V13 §2.7, line 1270; V13 §5.8 (8), line 3190). The scrub says where it is partial: before the first plate, beyond what the pulse records hold, the interior weeks of a multi-week advance the host did not send, a store the host's quota dropped (`W_LENS_PLATE_GAP`) (V13 §5.8 (8), lines 3202–3204). A quantity that decays, such as moral drift, is replayed only by the host's arithmetic as sent, never by a designed curve (V13 §5.8 (8), line 3204; lens-implications.md §4.6, line 492).

### The canon, versions and digests

A "digest" is a fingerprint: a short number that changes if any byte it covers changes. The "canon" is the world as frozen into the host's record.

**Every world document names every version it depends on.** The version table (`WorldRecipe.snapshot`) holds the generator's output version, the file schema (`schemaVersion`), the table versions W0–W9 read, the charter schema's version (`FrameCharter.version`), the adapter's pinned import version and the export schema's version (V13 §2.7, lines 1260–1264). An older charter is migrated by its own migration chain, never by re-generating the frame (V13 §2.7, line 1266).

**The canon's versions are per slot, never the file format alone.** The slots are the geometry (the generator and a hash over the physical layers and the member seats' points), the cost law as the host handed it in (version and hash), the travel law's version, the adapter folder's vocabulary tables, and the water and sites slots' input hashes; a slot whose inputs did not change is byte-identical (V13 §2.7, lines 1267–1270). So a change in one part never forces the host to re-read the others.

**The birth canon and the second digest builder.** A new world from the map module is canonized at the campaign's birth, the product ruling the host implements, never gated by its premium canonize entitlement; it waits only on H5, H7, H8 and H12, and V13 §11 Q4, which the owner answered on 2026-10-18 (V13 §8.5 preamble, lines 3715–3719; row H22, line 3747). Until it lands, a lens opens in its uncanonized regime (V13 §8.5 preamble, line 3720). H5 builds a second builder of the host's frozen record over the canon, its reader-facing shape unchanged, with a conformance fixture: one fixture, two builders, identical results (V13 §8.5 row H5, line 3730; fp-realm-review.md §5 row H5, line 652).

**Who stores the world.** On a host-bound world the host stores the world document per campaign beside its settlement map records — snapshot, log and backups under the frames' store pattern and lifecycle (V13 §2.7, lines 1271–1273; V13 §8.5 row H10, line 3735). A settlement map opened without its world falls back to its recorded charter values and refuses placement edits (V13 §2.7, line 1273). Budgets: a continent world at most 24 MB gzipped, a realm 11 MB, a province 3 MB, with at most 10^5 reason records (V13 §2.7, lines 1296–1298 and 1304–1305).

**What the world's digest covers, and what it does not.** The model digest covers the raster chunks, surfaces, reaches, watersheds, routes, territories, proposals, placements and traces; glyphs and lens plates are caches outside it (V13 §2.7, lines 1276–1281). A placement is in the world's digest and in no settlement map's: moving a settlement on the world map leaves that settlement's own model digest byte-equal, only its records digest changing by the charter event (T-V13-2; V13 §2.7, lines 1281–1288). The same holds for a free-standing site (SW-11), and `surfaceSetDigest(doc, week)` fingerprints the water surfaces in force at a week (SW-25; V13 §2.7, lines 1288–1295).

**Reading the host's own stored maps.** The map reads two pinned formats of the reference generator's full JSON export: 1.114, the host's own fork, through which each stored snapshot is read once; and 1.152, users' own files, with a `.map` file of 1.152 or later read through `mapFile: true` and an older one refused with the nearest supported version named (V13 §2.8, lines 1312–1320). The host supplies the export through one read-only bridge command for the loaded snapshot (V13 §8.5 row H1, line 3726; fp-realm-review.md §5 row H1, line 648). On the host's own snapshot (`origin: 'host-embedded'`) the file's settlements, states, provinces and cultures are dropped as inputs; the campaign's settlements arrive as the host's `importSeats` request, a legacy settlement matching a placement folded into it, any other kept as a hint (`W_IMPORT_LEGACY_BURG`), each host gate carried as a `HostGateRef`, and no settlement map is generated by the import (V13 §3.15 (3), lines 2731–2750; V13 §2.8 settlement row). Religions, military, economy and the like are dropped as host facts (V13 §2.8, last two rows).

**One coordinate transform, recorded for the host.** Every imported point uses one rule: cmPerPx = units per pixel × metres per unit × 100; x in cm = round(xPx × cmPerPx); y in cm = round((heightPx − yPx) × cmPerPx), because the file's y runs down and the world's runs north (V13 §3.15 (2), lines 2716–2721). The rule is written into the import report so the host can map its own pixel-keyed facts the same way, and the host keeps one coordinate adapter in both directions (V13 §8.5 row H6, line 3731). The report (`ImportReport`) lists scale, transform, hemisphere, dropped and unmatched items, and placements converted, folded, sited unverified or unresolved, kept on the world as a reason record (V13 §3.15 (4), lines 2756–2760).

**Who writes what.** The lens record (`LensLayer`) is the map module's own, with no host shape (lens-implications.md §4.1, line 406). The host's side is the world port's messages: outbound `canon`, `derivedFacts`, `mapFeed`, `routes`, `routeFacts`, `patrolOffer`, `pathGeometry`, `borderSegment`, `placeOf`; inbound `bindSeat`, `unbindSeat`, `importSeats`, `events`, `costLaw`, `travelLaw`, `hostRequires`, `canonized`, `consumed`, `genesis`, `network`, `polity`; presentation `clock`, `hostOverlay`, `beliefView`, `audienceKnowledge`; the offer `physicalChange` (fp-realm-review.md §5 row H4, line 651; V13 §8.5 row H4, line 3729). No port call happens inside a tick; answers are baked with their stamps (V13 §8.5 row H4, line 3729).

**Host exports change no simulated byte.** Every optional host read lands switched off and data-gated, absent meaning the prior bytes; within H23–H30 the exports change no simulated byte, and the clauses that would change behaviour are offers the host may decline, no lens waiting on any of them (V13 §8.5 preamble, lines 3705–3714). Patrol coverage and the sway, if the host consumes them, reach it only through its own readers: coverage re-priced by its one distance reader and read by outcome rolls only, the sway as an advance-start overlay at most one advance stale, stamped `swayRevision` (V13 §8.5 row H16, line 3741). Never a time or a cadence from the map (V13 §8.5 row H16, line 3741).

### The two closing rules

Every lens names the campaign's actual rules before it draws, from the regime the host resolved and never from a preset's name, and an element whose switch is off is drawn as "still" with its reason — listed greyed but openable, never hidden, never an empty map, never extrapolated (V13 §5.8 (2)–(3), lines 3133–3145; lens-implications.md §4.2, line 420). Every lens opens DM-only, a row sent with no resolved audience is folded DM-only, covert links, columns and patrols are omitted rather than greyed, and a player sees only rows the host resolved public or, where belief is recorded, the party's believed rows (V13 §5.8 (7), lines 3179–3187; lens-implications.md §4.5, line 467).
