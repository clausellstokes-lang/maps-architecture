## 1. Legend

**Tier** (owner product scope, 2026-09-25). **BASE** = an MFCG/FTG-class capability the stage-1 town/city generator
must cover at parity (parity is the floor; the architecture may meet it by an original technique). **STAGE-2** = an
NG-class capability the district→neighbourhood interface must be ready for. **VILLAGE-LATER** = a VG-class capability;
the only check is that the base does not preclude it. **STAGE-3** (added by this audit for the one row that concerns a building-interior hand-off) = a stage-3 hook check, marked `NOT-PRECLUDED` / `PRECLUDED` like VILLAGE-LATER. Rows in this slice are overwhelmingly BASE because MFCG is a base
reference and TownGeneratorOS is its ancestor; the few rows that describe another product inside an MFCG source take that
product's tier.

**Ref** = which reference variant the row records: `OS` (TownGeneratorOS 2017 source), `MFCG` (live generator, from
creator posts/devlogs or our recordings), `OS→MFCG` (one capability with a version ladder). Per-reference variants are
kept as separate rows when the technique differs materially; otherwise the ladder is noted inside one row.

**Coverage.** `COVERED` (cite the ARCHITECTURE.md section) — the capability is specified to a depth a builder can
implement without inventing the capability itself (original techniques that replace the reference technique count, and
the replacement is named). `PARTIAL` — the capability is present but a named part is missing or left unspecified.
`MISSING` — no section provides it. VILLAGE-LATER and STAGE-3 rows are `NOT-PRECLUDED` or `PRECLUDED` (with the reason). One extra mark, used for 2 rows: `NOT-REQUIRED` — the row records a defect of a mechanism the architecture replaces, or an option the reference itself removed, so the base owes it nothing.
Reference *defects* appear only where they are load-bearing for the reference's look or are failure modes a generator must
handle; for those, COVERED means the architecture states its own decision, not that it copies the defect.

**Sev** (PARTIAL/MISSING only). `H` = a parity-floor gap in a user-visible BASE capability or a model gap that would
block stage 2; `M` = a secondary BASE capability or a rule/parameter the builder would have to invent; `L` = cosmetic,
editor nicety, or a reference detail whose absence is defensible.

**Evidence tags** (from the findings files): `ST` stated by the creator or readable in the 2017 code; `SH` shown in our
recordings; `IN` inferred by a reader; `NO` named only; `CR` critic ruling or addendum; `exec` re-executed by a reader.
