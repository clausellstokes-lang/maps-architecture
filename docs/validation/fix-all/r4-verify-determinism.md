## 0. In plain words

This seat re-checked, after the fourth fix-all round was merged, the part of the design that makes the same seed give
the same town, keeps edits safe and handles failures. **All eight items handed to this area are now answered by a
concrete mechanism in the text.** A pond drawn inside a block, or a river widened into its riverside blocks, now clears
exactly the area it shows the user before the water goes in, so it no longer forces a rebuild of the whole town.
Opening a saved town now re-computes the fingerprint of the copy being opened before the first edit, and a copy that
does not match is treated as damaged and rebuilt from its recipe. Choosing your own street-name list, or editing a
naming rule, now renames the names that list or rule produced, after you confirm them. A name list you selected and
later deselected stays in the file. In a shared town, the owner's "keep the saved town" now reaches every other player.
Background checking and a big edit no longer need more memory than counted. The wall-strip rule now asks each edit
which walls it rebuilds. And the re-rollable settings in a recipe are typed as strictly as everywhere else. Every
earlier fix in these sections still holds, and no sentence here postpones anything.

The check found **ten new problems**, one of them serious. **The serious one: the new fingerprint checks compare
fingerprints made by different program versions.** A town saved with an old version and opened as a read-only view
will almost always be reported as "does not match its own fingerprint", because the current version computes some
parts differently. Worse, a town the owner once chose to keep from its saved copy would become read-only after the
next program upgrade, for the same reason. The fix: check each saved copy with the program version that wrote it, and
record the new fingerprint when a town is upgraded. The nine smaller ones:
- In the fallback for slow machines, the user could "trust the saved town" before its fingerprint was checked.
- A name the user renamed and then un-renamed loses the record that lets a later name-list change find it.
- The renames an edit asks the user to confirm have no place in the edit's record.
- Choosing a new street list for one culture would also rename that culture's district names.
- The saved records that steer later renames and faithful regenerations are never checked on opening.
- A name-list selection that the user undid and can still redo is dropped from the file at the next save.
- A share link can be made for a town kept from its saved copy, and it would show a different town.
- An upgrade does not save a setting pack that the new version stops shipping.
- One rule elsewhere says a new bridge is placed in the opposite order from how the river-moving edit places it.
