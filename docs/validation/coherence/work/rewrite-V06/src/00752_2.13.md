### 2.13 Item 110's epoch records — the reason key, the ledger and the suppression

```ts
type RaisedKind = 'viaduct'|'elevated'|'aqueduct';
interface RaisedReasonKey { kind: RaisedKind; a: Id; b?: Id }
  // viaduct: a = the carried way's lineage, b = the crossed ravine or valley feature (the terrain's lineage and the feature's ordinal in Terrain.features);
  // elevated: a, b = its two endpoints' lineages (a high ward's district, a terrace district, the citadel's or a great temple's reservation), in address order;
  // aqueduct: a = the settlement root, b = the source (a spring as S1 records it, or a river WaterBody's lineage).
  // Address: 'raisedReason:' + hash64(kind, a, b) (§6.3). It is also the generated raised way's derivation unit (V06 §3.16).
type SpanRef = { raised: Id; from: number; to: number }   // the spans between two supports of a raised way, by support ordinal; a view resolved in its batch, never stored in a record (as §2.2's StretchRef)
interface RaisedCandidate { key: RaisedReasonKey; value: number /* the reading: the drop (m), the rise (m) or the need ratio */; threshold: number;
  strength: number /* metres saved − span × spanCostFactor; mean prosperity × landmark factor; the need ratio */; met: boolean;
  u?: number; p?: number /* the gate, when met */; outcome: 'admitted'|'repaired'|'standing'|'chance'|'cap'|'suppressed'|'noCourse'|'capsCannotPay'|'rung';
  /* 'suppressed': a key a live removal holds and no re-add serves — read and gated as any other, never admitted (V06 §3.19.3 (2)); a served key reads 'standing' */
  why: WhyRow[] /* the rows written on the creation event (V06 §3.19 (8)) */ }
interface RaisedWayLedger {   // derived, never persisted: at each epoch's raisedWays step and at each generation (BCR-V6-25)
  rung: Rung; gate: boolean /* the rung admits generation: CITY or METROPOLIS (owner provenance) */;
  kinds: Record<RaisedKind, { cap: number /* V11's raisedWays row at the rung */;
    standing: Id[] /* generated raised ways that count: every generated way not released (V06 §3.19.1 (3)) */;
    declared: Id[] /* raised ways whose lifecycle cause is an edit or a skeleton file (the dossier declares none, V06 §3.19.1 (2)) */;
    suppressed: RaisedReasonKey[] /* the reasons the log's live removals suppress */;
    count: number /* standing + suppressed + declared (V06 §3.19.1) */; candidates: RaisedCandidate[] /* every key evaluated, admission order */ }>;
  total: { cap: number; count: number } }
// BCR-V6-24: added to §2.8's LifecycleEvent.detail beside BCR-V6-20's `why`
suppress?: { kind: 'raised'|'harbourChain'|'quayWall'|'retaining'|'deckPlot'; key: string /* the suppressed generator key's address */;
  reason?: RaisedReasonKey /* kind 'raised' */; enceinte?: Id; water?: Id /* harbourChain: the enceinte and the harbour basin whose mouth it closed; quayWall: the enceinte and the water body of its waterfront arc */;
  chain?: string /* retaining: the deleted wall's chain lineage address */; host?: Id; slot?: number /* deckPlot: the deck host's id (item 246) and the deleted plot's slot ordinal along the deck from its host's first end */ }
// islands and sky accesses keep volume 5's record form (SkyIsland.removed, .removedAccesses): an island's removal holds a count-law slot and an archived arena, which a
// suppression key on a delete event cannot hold; both forms read the one lift rule of file f item 260 (§2.8) — kept apart by ruling E-02
```

The ledger is a pure function of the model and the log: its suppressed set is the `suppress` of every `delete` in the log
whose event is live (not undone), kind `raised` (the other kinds are read the same way by their own generators: the
waterfront rule, the levelling's walls and tier (5)'s deck faces); its counts read the standing raised ways' `reason` and lifecycle cause. It is exported by
the package that holds the base's raised-way generator (BCR-V6-25) and called by the pass (V06 §3.19), by generation's S4
and S6 and by a new stage's S5b, so no generator can exceed a cap or re-found a suppressed reason on any path.

### 2.14 The history replay's records (item 113)

```ts
interface ReplayEvent { type: string /* a history event type (SettlementForge's 29, or a scar type of HistoryHint) */; yearsAgo: number; severity: number /* 0–1 */;
  row: string | null /* V11's event-to-epoch row it maps to (`history.events`); null: unmapped — reported (`replayEventUnmapped`), played as nothing */ }
interface ReplayEpoch { r: number /* 1 … of, oldest first */; of: number;
  fromYearsAgo: number; toYearsAgo: number /* the span (toYearsAgo, fromYearsAgo] before the present; the last epoch ends at 0 */;
  week: number /* creationWeek − round(52 × toYearsAgo): a week at or before the creation week (V06 §3.20.3) */;
  populationTarget: number; events: ReplayEvent[] /* the history's events inside the span, in yearsAgo order (oldest first), then type */;
  destroyed?: { cause: 'terminal'|'catastrophic'|'fallOf'; yearsAgo: number } /* DR38: the settlement is destroyed in this epoch */;
  refound?: { population: number; culture?: string /* the history's culture row from the refounding on, else the present one */ } /* DR38: the new settlement generated on the ruins in this epoch */ }
interface ReplayPlan { peak: HistoryRecord['peak'] | null /* DR36, §4.11 History-first (1) */; peakYearsAgo: number | null;
  startsAt: 'founding'|'peak'; startPopulation: number; epochYears: number /* V11's history.epochYears, or the bent value (V06 §3.20.1) */; bent: boolean;
  epochs: ReplayEpoch[] }   // derived from the recipe's history and the tables pinned in the recipe (V06 §3.20.1); never persisted
interface HistoryReplay {   // @plat/evolve; called by generation after S13a when history.replay is on (§4.11 History-first generation (2))
  plan(history: HistoryHint /* the recipe's history (§2.7): V08 fills it from the dossier, V09's editor from the blueprint's history option */, tables: TableView, present: { population: number; rung: Rung }): ReplayPlan | null /* null: no replay (V06 §3.20.1's cases) */;
  run(doc: DocView, plan: ReplayPlan): KernelResult<{ record: HistoryRecord; epochs: number /* folded */ }> /* appends and folds one creation-prefix epoch per plan epoch through the runner (W1) */ }
```

The replay's epochs are ordinary `epoch` events of the creation prefix (V06 §3.20.3): no new event kind. What the base
record carries of them is `HistoryRecord.epochs` (§2.7), written from `ReplayEpoch` at the replay's close (V06 §3.20.6).
