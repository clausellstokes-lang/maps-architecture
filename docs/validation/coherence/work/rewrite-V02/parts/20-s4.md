
## 4 Editing

### 4.1 The declarations — the ops of `setMassing` and `setComposition`

Item 101's rule is kept: no thirteenth tool. The building tool T9 `shape` (L3) gains parameters, each an existing
event or one of the two event kinds `setMassing` and `setComposition` that §7.1 declares (item 351); this section
declares their ops. A new building is still T6 `place` / `build`, whose S11 run is the massing.

```ts
type MassingOp =
  | { op: 'family'; family: MassingFamilyId }                                                   // re-lay the building as another family: V02 §3.9 W1–W9 with that family, the current wings the seeds; draws on siteplan.mutate (V02 §3.12)
  | { op: 'addRange'; from: PointsForm /* two points: the range's centre line (item 101 (i)) */; widthCm?: Cm; floors?: number; role?: 'range' | 'cross' | 'service' }
  | { op: 'reshapeRange'; wing: number /* key */; ends?: [PointCm, PointCm]; widthCm?: Cm }    // the centre-line and width handles
  | { op: 'addTower'; from: PointsForm /* one point: the centre */; radiusCm?: Cm; shape?: 'round' | 'square' | 'octagon'; turret?: boolean; floors?: number }
  | { op: 'moveTower'; wing: number; at: PointCm; radiusCm?: Cm; shape?: 'round' | 'square' | 'octagon' }   // shape: the ring re-made at the same centre and radius
  | { op: 'addBlock'; wing: number /* the host range */; at: PointCm /* on its ridge */; lengthCm?: Cm; depthCm?: Cm }
  | { op: 'backRange'; on: boolean; lengthCm?: Cm; widthCm?: Cm; side?: 'left' | 'right' }
  | { op: 'removeWing'; wing: number }
  | TiersOp;                                                                                     // V02 §4.6
type CompositionOp =
  | { op: 'dormers'; wing: number; eave: 0 | 1; count: number; widthCm?: Cm; kind?: DormerKind }
  | { op: 'porch'; kind: PorchKind | 'none'; widthCm?: Cm; depthCm?: Cm; entrance?: number /* an Entrance ordinal: set → the secondary porch at that side, rear or yard entrance (a hood or none) */ }
  | { op: 'room'; role: 'hall' | 'gatehall' | 'chapel'; on: boolean; fromCm?: Cm; toCm?: Cm /* the extent along its host's ridge, from the host's ridge start */ };   // V02 §3.8's rooms: on or off, and their extent
```

Storeys and roofs of one wing are the base's `setAttr` on `wings/<key>/heights/floors` and `wings/<key>/roof` (`kind`,
`pitch`, `high`), addressed by key (§7.1; item 351). A lock on `wings/<key>` (an attribute-level lock, §7.2) holds that
wing against every mutation, re-derivation and edit of another wing. Re-rolls are the base's `regenerate` with `rung:
'wings'` or `'rooms'`; the massing's re-roll is New random on the building's plot. **Draws** (J-V2.18; V02 §3.12): the
geometric ops draw nothing — a default an op leaves out is the row's deterministic central value (the midpoint of a range
cell, the heaviest weight of a weighted one); the `family` op draws on `siteplan.mutate`, a pure function of its key, so a
replay is exact either way.

**No refusal but a lock or a dossier fact** (item 101 R2; J-V2.79; J-VI.4). Every infeasible op of this section and of
V02 §4.6 is **bent** to the nearest lawful one and named in one line with its closest alternatives, under an id of
V02 §1b's bend row (`bend.<…>` below); V09 §4.9 words each id and V10's clerk says it (X21, X22). A bend draws nothing
(V02 §3.12), is one undoable event, and replays from a skeleton file to the same bend. An op on a locked wing, or one that
would move a locked wing, is refused with the lock named; with a dossier fact (item 20) these are the only refusals.

### 4.2 What each `setMassing` does — dry run, commit, locality, undo

1. **The new wing set, as values.** `family`: V02 §3.9's steps, recorded as `MutationStep`s in `EditBase.mutations`; a
   `family` op into or out of `stepped` also writes the use's stepped specialisation in the same undo group (V02 §4.6 (1)).
   `addRange`: the points form's two points (snapped; the authoring boundary's resampling and snap, §7.1) are the centre
   line; width as given or the row's middle width; an end within `w` of another range's long side ends on that side (a
   butt joint, the new range abutting); an end within `w/2` of another range's free end, turned by more than 2°,
   mitres with it; role `range` unless given; floors as given or the `main` wing's; roof by the role's default kind.
   `reshapeRange`: the ends and width move; every range abutting it is re-trimmed to its new side; a block on it is
   re-split (V02 §3.5 M7). `addTower`: the one point is the centre; radius and shape as given or the row's middle; floors
   one above the tallest wing it meets. `moveTower`: the same tests at the new centre; a new `shape` re-makes the ring at
   the same centre and radius (the room and stair of a stored plan re-cut by the plan rung). `addBlock`: V02 §3.5 M7 on
   the host at the given point. `backRange`: V02 §3.5 M9 on or off with the given sizes and side. `removeWing`: the wing
   leaves (its key is never re-used); a removed block's host pieces re-join into one wing that keeps the lowest of their
   keys; **removing the `main` wing passes the role to the longest remaining range** (ties by key). The bends of this step:
   * `removeWing` of the building's last wing → T6's `remove` of the building, one undoable event (`bend.building.remove`:
     "Removed the building with its last wing");
   * `reshapeRange` on a row quad — whose party walls are the plot's (J-V2.13) — for its ends' moves along the frontage →
     the plot edit that moves that party-wall line: the plot's `moveVertex` on the line's frontage vertex, the neighbour's
     quad re-clipped by S11, both in one event (`bend.row.plotLine`; a lock on the neighbour's quad or plot is refused
     with the lock named, R2's second class); for its width (the quad's depth into the plot) the op re-cuts the quad's
     rear chain at the new depth inside the plot and the back region, the quad then an edited, pinned wing;
   * `removeWing` on a row quad that is not the building's last wing removes it — a gap in the row, the neighbours'
     party-wall ends reclassed as gables by the roofscape (V02 §5.2 step 1), the remaining wing taking `main`;
   * a `family` op whose family is unreachable or infeasible on the building → the reachable, feasible family nearest
     it — the fewest growth-lattice steps, ties by the target row's weight — naming the least plot the asked family needs
     and offering `join` (`bend.family.nearest`).

   Every writer re-sorts the wings into the canonical order (V02 §2.1) and rewrites `MassingRef.segments` before the dry
   run's checks.
2. **The dry run** (on the overlay, §7.1): the region the edit may use is the plot less the footprints of the plot's
   other buildings, each buffered by `attractCm` (§3.2) — so a hand may build to the plot line, never over a neighbour, a
   passage's other side or a way. The checks are V02 §3.5 M13's (tiling apart from towers, containment in that region, the
   ring rules, `minEdge`) and M8 (ii)–(v) for any tower; M10's budget is not applied to a hand edit (the capacity follows
   the shell). A failing op is bent to the nearest lawful one: a range crossing the region's boundary, or an op reaching
   beyond the plot, is clipped to it, the line offering `join` with the neighbour (T9's `join`, §7.1) as the way to more
   land (`bend.wing.clip`); a tower that would stand through a wing moves outward along the line from the wing's nearest
   boundary point by the least distance that passes (iii) (`bend.tower.move`); a range overlapping another is trimmed to a
   butt joint (`bend.wing.trim`); a wing below 4 m² or with a side below `minEdge` is grown about its centre line to the
   least lawful size — its width first to 2 m, then its length until 4 m² — inside the region (`bend.wing.grow`). **The
   dry run also lists**, from V03's `plan` query, every stored-plan room, edited opening and furnished room the op would
   orphan (V03 §3.11, V03 §4.3), each with §7.3's orphan actions — the `tiers` op's dry run among them.
3. **The commit** runs S11's operator on the plot with the building's new wings as fixed (the path `moveFootprint`
   already takes, §2.6 rule 5): the footprint face re-inserted with the plot's other buildings fixed, `deriveBase`, the
   entrance set re-derived (an edited entrance kept, §7.2; the massing's entrance hint re-read), the basement re-derived
   unless edited — **keeping the crypt** of an `always` class with no condition, and a `basement`-class church's while its
   class stays in the church family, the cathedral's by the no-refusal ladder and its wet-ground lift (V02 §3.14.5) — the
   yard partition re-fitted (a new hole typed `court`, item 303), the capacity function re-read and any excess re-homed by
   §4.7's overflow pass, the first carry; for a stored composition, its re-match by key (V02 §3.9 W8); a **stored plan is
   re-cut inside the event** by V03 §3.11 around its edited parts. An unstored `wings` rung is marked stale.
4. **Locality (§7.3 item 1).** The effective scope is the plot (its faces and buildings), the passage a wing spans
   (the base's rule) and the buildings receiving re-homed households; T-V2-19 checks that nothing else changes.
5. **Undo** keeps the former wings, `Building.massing`, `nextWingKey`, the stored composition and everything S11's
   re-fit changed (§7.4's S11 rows); undo restores them exactly, a re-homed household's former building included.

### 4.3 What each `setComposition` does

The first `setComposition` on a building **stores its composition** — the current derived composition, with the op
applied — as `Building.composition` (§2.6's rule for the first composition or plan edit), its record `edited`.

* `dormers`: the count is clamped to the eave's bays (`facadeBays`, V02 §3.7) and named when clamped
  (`bend.dormers.count`); the row is marked `edited` (a fixed input to the plan rung's dormers, V03).
* `porch`: a kind whose space fails (V02 §3.7) is bent to the nearest feasible kind; with `entrance` the op sets or
  removes the secondary porch there, a hood — any other kind there is bent to a hood (`bend.porch.kind` for both).
* `room`: turns the hall, the gate hall or the chapel on or off and sets its extent along its host's ridge, bent to the
  nearest lawful extent by V02 §3.13 (3)'s rule (`bend.room.extent`); the room is marked `edited` (a fixed ring for the
  plan rung) and kept through a re-derivation of the `rooms` rung while its host keeps its key; a stored plan is re-cut
  inside the event by V03 §3.11, the dry run listing what the op would orphan as V02 §4.2 step 2 does. Turning a room on
  where no host admits it bends: a gate hall without a `gate` range becomes a **gate passage** through the wing carrying
  the main entrance — from eave side to eave side at the entrance's offset, the row's central `gateHallM` wide, its two
  ends arches to the street and to the yard behind (`bend.room.passage`); a hall or chapel goes to the `main` wing, else
  the largest storeyed wing (a chapel at its east end by V02 §3.8's rule); on a building whose wings are all solid, the op
  first turns the tiers above tier 0 storeyed (the `tiers` op's `solid: 'lower'`, V02 §4.6) and then places the room in
  the lowest of them (`bend.room.host` for both, each step named).

The effective scope is the building. Undo restores the former composition, or removes the stored one when this event
stored it (J-P48 (5)); the rooms and plan points the stored composition holds are carried by `carryWings` (§2.6); its
composed wings and towers follow their base wings by key (V02 §2.2).

### 4.4 Lifecycle, orphans and the control

**Lifecycle.** The two kinds' row is §7.4's `setMassing / setComposition` row (item 351); the `tiers` op and every bend of
this section fall under it unchanged. What this volume adds to the row: an edited dormer row is also a fixed input to the
plan rung (V03); a secondary porch migrates by its entrance ordinal.

**Orphans (§7.3's orphan table; J-P48).** An edited dormer row whose eave changed length by more than ± 10 % (V02 §3.9 W8),
an edited room whose host key left, and a secondary porch whose entrance left are listed in §7.3's orphan table with two
actions: **re-attach** (a dormer row to the same eave of the same key, its count clamped to the new bays; a room to its
role's lawful host by V02 §3.8, its extent clamped; a porch to the nearest side, rear or yard entrance) and **discard**
(the derived value returns). Nothing orphaned is dropped silently.

**The control.** `fantasyShapes` is §7.8's stage-3 model control (item 402; documentation anchor V02 §3.3), in the
advanced panel. The `FM` building look (V02 §3.10.8) is a style choice for V09's style panel (X10); it changes no model
byte.

### 4.5 The canvas, the clerk and the skeleton file

* **Canvas handles** — V09 draws them (V09 §3.5; T-V9-42); this is their contract: at the building band, each range shows
  its two centre-line end handles and one width handle (drag → `reshapeRange`), each tower its centre and radius handles
  (→ `moveTower`) and a shape chip (→ `moveTower { shape }`), each wing a storey stepper and a roof-kind chip
  (→ `setAttr`), each eave a dormer stepper (→ `setComposition dormers`), the main entrance a porch chip and every side,
  rear or yard entrance a hood toggle (→ `setComposition porch`), and — at the building band with the plan shown — the
  hall, gate hall and chapel an on/off chip and two extent handles along their host's ridge (→ `setComposition room`); a
  **family strip** shows the feasible families of the building's row, each as a ghost made by a dry run of `setMassing
  family`, one tap committing it. Every drag previews its dry run live inside the plot (§14's interaction contract) and
  commits one event on release.
* **The clerk** (V10) calls the same operations through the tool API (§11.2): "make the manor an H" is
  `setMassing { family: 'H' }`; "a round tower on the north-east corner" is `addTower` with that corner's point;
  "two dormers on the street side" is `setComposition dormers` on the `main` wing's street eave. It reads a building's
  massing (family, wings with roles, storeys, roof kinds, towers) and composition (dormer rows, porch, rooms) through the
  reader, under §9.2's knowledge rules — the mass of every building is public (J-A30.83), and nothing in this volume is
  concealed (a front's concealed rooms are the plan's, V03).
* **"Why is it this shape?" — the `WhyProvider`** (J-V2.51; the why query is V10 §3.9's). `@plat/buildings` registers a
  provider for the kind `building` at the paths `massing`, `wings/<key>` and `composition`. It fills V10's `WhyAnswer`
  without a new field: **`facts`** — `massing/family`, `massing/row` (the key the chain reached), the manifested band and
  value, the drift bounds, `fantasyShapes`, `massing/segments`, `massing/axis` with `MassingRef.low`, each wing's role,
  floors and roof, and the **alternatives** as fact rows — `massing/alternatives/<family>` = its renormalised weight among
  M3's feasible families (or `infeasible: <the failed test>`), `wings/<key>/rejected/<i>` = the M8 test (i)–(v) a
  rejected tower candidate failed, `composition/porch/d` and `composition/porch/feasible`,
  `composition/dormers/<key>/<eave>/dropped` = the obstacle of a dropped dormer — each with `tier: 'derived'` and `row`
  the `composition.json` slice; **`cause`** — S11's massing (`step: 'S11'`, `rule: 'V02 §3.5'`, `chance: 'massing'` with
  its creation index), the `setMassing` event (`seq`), or the mutation's W1 draw or kept seeds (W2; `chance:
  'siteplan.mutate'`); the sunlit choice names `sunBias` and the options' factors; each bend taken is the fact
  `massing/bend/<id>`. The alternatives are **recomputed** by re-running M3 and the M5/M8 tests on the committed state
  without advancing any stream (a pure function), so the answer on an untouched building equals the massing's recorded
  draws (T-V2-43). "Why no crypt / why this crypt" is V03's and V04's provider (item 238's `Basement.crypt`).
* **A skeleton file** carries these events as ordered declarations like any other (§11.1): a building declared with
  `build` then shaped by `setMassing` lines is re-created exactly by the creation prefix's fold (§4.1's read-ahead reads
  no stage-3 declaration ahead; the massing runs when its plot's S11 runs, and the declared ops apply at their log
  positions).

### 4.6 Editing stacks and deck buildings

```ts
type TiersOp = { op: 'tiers'; count?: number; insetCm?: Cm; top?: 'flat' | 'shrine' | 'roofed'; stairs?: 'axial' | 'flights' | 'internal' | 'none';
    stairWidthCm?: Cm; shape?: 'rect' | 'round' | 'octagon'; lowerRoof?: 'flat' | 'pent'; solid?: 'all' | 'lower' | 'none';
    shrineInsetShare?: number; centre?: PointCm; radiusCm?: Cm };
    // re-lay a stepped building's stack on its tier 0 (layTiers' anchored mode); on any other building it first bends to family 'stepped'
```

Every limit of a stack, a deck or a row below is a bend under V02 §4.1's rule; undo restores the building's leaf digest
exactly.

1. **The `tiers` op.** On a building that is **not stepped** it bends to `setMassing { op: 'family', family: 'stepped' }`
   followed in the same event by the op's values (`bend.tiers.stepped`: "Made it a stepped building first") — V02 §3.15.5's
   anchored `single → stepped` on the building's `main` range, through `single` by the growth rows, drawing on
   `siteplan.mutate` as a `family` op does; where W1's anchored test fails, `bend.family.nearest` (V02 §4.2) applies.
   **The stepped specialisation (J-V2.94).** This bend, and a `setMassing { family: 'stepped' }` op, write in the same undo
   group (§7.1's `EditBase.group`) an `editTable` row op on the use's `siting.declared` `use:` row (V11 §4.2), setting its
   cell `specialisation` to the id of V11 §3.24.3's row for the use's culture and class where one exists, else
   `stepped_temple` for a class of the worship family, `terraced_palace` for `palace`, `tiered_tower` for `tower_house`,
   `mage_tower` or `watchtower`, and no cell for any other class (its own plan rows stay) — so `Use.specialisation`, the
   heights row where the specialisation names one (`stepped-shrine`) and V03's plan rows follow the hand-made stack, held
   and exempt from the chance and the cap (V11 §3.24.3). A `family` op from `stepped` to another family on a use holding a
   stepped specialisation writes `specialisation: 'none'` the same way. Undo removes the row op with the event; a skeleton
   file replays both lines.
   **On a stepped building** the `tiers` op re-runs `layTiers` in anchored mode on tier 0 with `MassingRef.stack` and the
   op's values, with no draw: a value the op leaves out keeps the stored one (the count: the tiers now standing; the step
   `stack.insetCm`; the grade `stack.grade`; the top; the stair form; the stair width: the current stairs'; the shape, the
   skirt, the solid mode and the shrine's inset as laid). **A new tier** takes the row's central values:
   `floors = max(1, round-half-up(central(tierFloors) × taper^k))`, or height `central(solidHeightM) × taper^k` to the
   centimetre. **Keys:** a kept tier keeps its key, and its ring and heights exactly where the step, the shape and the
   stair form are unchanged (else its ring is re-inset, its key and heights kept); a stair keeps its key across a change of
   stair form while its tier stands (its ring re-laid), and is removed with its tier or under `internal` or `none`; tiers
   above the new count are removed with their stairs and every wing standing on them (keys retired); new tiers and stairs
   take keys from `nextWingKey`; the shrine comes and goes with `top`.
   **The fields and their bends:**
   * `count` above what fits → the most that fits (`bend.tiers.count`); `insetCm` that leaves no second tier → the
     largest lawful step (`bend.tiers.step`).
   * `stairs`: `flights` on a round or octagonal stack → `axial` (`bend.tiers.axial`); **`internal` over a solid tier
     0** → `none` where every tier is solid, else `axial` (the first form of J-V2.74's order; `bend.tiers.none`,
     `bend.tiers.axial`); `none` over a storeyed tier 0 → `internal` (`bend.tiers.internal`); where the reserve of the
     asked form does not fit in front of tier 0 inside the plot, the forms are tried in J-V2.74's order, and where none
     fits the current form is kept, named with the depth the asked form needs (`bend.tiers.form`).
   * **`none` — the sealed stack:** lawful wherever tier 0 is solid; ST3 uses `d` on every side, ST5 lays no stair, ST6
     skips the chain check, `stairChain` is empty and `landingSide` null; a storeyed tier or shrine on it is reached by
     nothing (V03's `W_TIER_UNREACHED`), which the line names.
   * `shape` re-lays tier 0 as the named shape inscribed in its current ring's bounding rectangle in the building's frame
     (a round or octagonal ring at that rectangle's inradius, a rect at the rectangle itself), the stack re-inset.
   * `centre` and `radiusCm` (a round or octagonal tier 0): tier 0 re-laid as the regular ring of that centre and
     circumradius, clipped by the least move to the plot region (V02 §4.2 step 2), the stack re-inset.
   * `lowerRoof: 'pent'` → `flat` where the stair form is not `internal` or `none` (equal insets; `bend.stack.roof`); a
     stair form turned `axial` or `flights` on a pent stack turns its lower roofs `flat` in the same event, named
     (`bend.stack.roof`).
   * `solid`: `'all'`, `'lower'` or `'none'`; a tier turning storeyed takes the row's central floors (round-half-up), one
     turning solid keeps its `eaveCm` (less any parapet) as its height; a stair form made unlawful by it bends by the rules
     above (`internal` over a solid tier 0; `none` over a storeyed one).
   * `shrineInsetShare` re-lays the shrine (ST4's tests); a shrine that no longer fits drops the top to `flat`
     (`bend.tiers.top`).
2. **A tier's height.** `setAttr(wings/<key>/heights/floors)` on a storeyed tier or the shrine,
   `setAttr(wings/<key>/heights/eaveCm)` on a solid tier (item 351's paths). Inside the same event `rebaseStack` re-bases
   every wing standing on it, directly or through the chain, and each stair whose rise changed is re-laid (ST5, its width
   kept): where the terrace no longer holds the run at the stack's grade, the grade steepens up to `stairGradeMax`; beyond
   that the height is bent to the most the terrace allows (`bend.tier.height`: "the stair up this tier needs room on the
   terrace below"). **`setAttr(wings/<key>/heights/baseCm)` on a wing with `on`** bends to the same change in the height
   of the wing it stands on — a solid support's `eaveCm` by the difference, a storeyed support's floors by
   `round-half-up(difference ÷ storeyCm.upper)` (a zero result a no-op, named) — then the rules above (`bend.stack.base`);
   a user's `baseCm` on a ground wing is kept (J-DET-24) and carries the stack through `rebaseStack`. From M3a to M6c the
   base's `setAttr` of a wing's heights (the wing's index, which equals its key) does the same through the base outline
   builder (item 229).
3. **Roofs on a stack.** `setAttr(wings/<key>/roof)` bends (`bend.stack.roof`): on a lower tier to `flat` or to its
   shape's pent kind (`hip` rect, `pyramid` octagon, `cone` round), the pent kind only under `internal` or `none` (else
   `flat`); on the top tier among `flat`, `hip` (rect), `pyramid` (octagon) and `cone` (round) — another kind bends to its
   shape's kind; on a stair to `shed`; on the shrine among the kinds of `TierCells.shrine.roofs`, else the first.
   `MassingRef.stack.lowerRoof` stays the laid default that a later `tiers` re-lay applies.
4. **The other `setMassing` ops on a stepped building.**
   * `reshapeRange` on tier 0 re-insets the whole stack from its new ring (keys kept; a tier that no longer fits removed
     with its stair and everything on it, named).
   * `removeWing` on **tier k ≥ 1** removes it, its stair (the stair whose `to` is tier k), every wing standing on it and
     every higher tier with its stair (named). `removeWing` on **tier 0** removes the stack — tier 0, every stair and
     every wing standing on it; any ground wings added beside it stay (the longest takes `main`, the family becomes
     `single`, `stack` is cleared), and with none left it bends to T6's `remove` of the building
     (`bend.building.remove`).
   * `removeWing` on **a stair** bends to `tiers { stairs: 'internal' }` where tier 0 is storeyed ("Removed the stairs; the
     tiers are now reached from inside"), else to `tiers { stairs: 'none' }` ("… the pyramid is sealed") —
     `bend.tiers.internal`, `bend.tiers.none`.
   * `addRange`, `addTower` and `backRange` are admitted as **ground wings** (no `on`; `bend.stack.groundWing` names the
     placement): each is laid by V02 §4.2's rules outside tier 0's ring, every stair's ring and stair 0's **approach
     strip** — the reserve's width, `landingM` deep in front of stair 0's foot (under `internal`, `landingM` in front of the
     main entrance; under `none`, no strip) — moved away from them by the least distance; a range ending within `w` of
     tier 0's side abuts it (a butt joint, rule 1's shared vertices), a back range takes tier 0 as its host (M9's rear
     side), and a tower passes M8's tests (ii)–(v) with tier 0 as its host wing and its ring clear of every wing standing
     on tier 0, every stair and the strip, its eave raised above tier 0's roof in its ring (M11). **`addBlock`** (a block
     splits a range, and a tier is not a range) bends to `addRange` of the block's size at the given point on the ground
     beside tier 0 (`bend.stack.groundWing`). M13's pairing then covers tier 0, stair 0 and the added wings; ST6's nesting
     is unchanged.
   * `family` runs V02 §3.15.5's rows.
5. **Deck buildings.** Every op works as on any building, inside the deck plot (V02 §4.2 step 2's region, which lies
   inside the deck's width); **a floors value above the deck's `maxFloors` is bent to it** ("a deck carries at most n
   storeys"; `bend.deck.floors`) — for `setAttr` of floors and `addRange`'s `floors` alike (J-V2.70); M10's budget is not
   applied to a hand edit (V02 §4.2), so the plot alone bounds the footprint; **a `family: 'stepped'` op on a deck building
