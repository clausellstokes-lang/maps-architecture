## 0 Verdict in plain words

Volume 10 is a strong, carefully reasoned design of the assistant: it keeps the assistant a client of the same tools a
person uses, it tries every change on a disposable copy before showing it, it never commits without the user's Accept,
it prices every turn, it survives being switched off, and it follows the provider's current guidance on the model, the
caching and the refusal fallbacks. It is not yet buildable as the owner's rules require, for three reasons that each
break an owner rule, and about twenty mechanisms that are wrong or missing.

The three that break owner rules. First, the answers the assistant receives can still reveal what a player may not
know: the types carry a secret place's class, the ids of the rules that name it, the goods it trades and a "kind" word
such as "a guild house", so a player's assistant could learn that a hidden house is a guild (item 63 (c)). Second, the
owner's newest underground rules (item 109, 19:15–19:55) are absent: a player's assistant would be told that there are
caves or ruins under the town that nobody in town has found, and it cannot explain ruins, how a way down came about,
why nobody lives in a sealed cave, catacombs that never shrink, or why a church has a crypt (the cathedral always, the
largest) while the catacombs lie under the cemeteries, as the owner switched it at ~20:05. Third, "the clerk never invents a dossier fact" is
enforced for the map but not for the assistant's words: a reply may state an invented fact about a SettlementForge
institution and pass every check.

The largest of the other problems: a shared map file can change which model the user's own key pays for and can put
text into the assistant's instructions; the "why" explanation claims to reproduce the placement score exactly, which it
cannot, because places are chosen one after another; a proposal that names something it just created can name the
wrong thing when the map moved meanwhile; SettlementForge's own assistant has no way to show its proposal card in the
map frame; the privacy projection for SettlementForge is missing the new question kinds; the village product (volume
7) is ignored, so "a village" becomes a small town; the history questions volume 6 promises have no way to be asked;
two details of the provider's refusal fallback and one caching rule are handled wrongly; the map frame's security
policy in volume 8 would block the assistant's network calls; and the fallback for a browser without direct access
names a desktop program the product does not have.

Each finding below states the exact change. None needs the owner except where section 5 says so; the owner questions
the volume asks are sound, and one (the evaluation's own spending) should be added.

## 2 Blockers

**C10-01 — blocker — owner fidelity (item 63 (c); §11.2 oracle rules (1)–(3), J-A101.85), lifecycle of knowledge. A
withheld place's purpose reaches the model through the types.** §11.2 withholds "the `name` and the purpose of a place
(its `use`, or an institution's kind)" and gives a withheld place "by its address and kind only". The volume's own
types carry the purpose in six places:
* `EntityCard.uses: { id; cls: string; withheld?: true }[]` (l. 628) — `cls` is required, so a withheld use still names
  its class.
* `EntityCard.attrs` (l. 624) lists "the registry's readable paths, ≤ 40" with no rule for a withheld entity, so `use`,
  `class`, `function`, `sector` or `powers` paths survive.
* `WhyPull.row` (l. 652) is V11's derived-row id — `cls/<class>/<n>`, `sig/<id>`, `sup/<class>/<resource>`, `spc/<class>`
  (V11 §2.4) — so a pull whose `target` is withheld still spells the target's class inside its id (`sig/tavern-smugglers_den`).
* `WhyLink.good` (l. 656) names the good even when `other` is withheld; a good can be the purpose ("stolen goods",
  "poison").
* `SiteCandidate.hardFails: string[]` and `WhyAnswer.alternatives[].hardFails` (l. 632, 641) are row ids with the same
  property.
* V10 §5.2 (l. 1465) writes a withheld place "as its kind (\"a guild house\")" — a class word, which tells a player the
  hidden house is a guild.
A seventh path: `read_map { kind: 'inView' }` "uses the session's view" (l. 897), and a view-bound reader admits a
`secret` row at the building band (§9.2's table). A name admitted that way enters the segment, the referents and the
transcript, which V10 §5.3 exports to "any role" — while §11.2 requires every band-less list or file to admit "as at the
city band".
*Required change:*
(1) **Kind words.** For a withheld target every `kind` field in `MapBrief`, `EntityCard`, `WhyAnswer`, `SiteCandidate`,
`CritiqueFinding.params` and the rendered map block is the entity registry's kind (§2.8: building, plot, use,
institution, …), never a class, use or institution kind. Its plain word comes from a new `clerk.json` row
`withheldWords: Record<registryKind, string>` ("a building", "a plot", "a business", "an institution"; own). V10 §5.2's
example becomes "a building".
(2) **Attribute allow-list.** BCR (new, on §2.8's registry): each readable path is marked `purpose: boolean`. For a
withheld entity `EntityCard.attrs` keeps only paths with `purpose: false`, and `EntityCard.uses[].cls` becomes optional
and absent. The same rule filters `WhyAnswer.facts`.
(3) **Row ids.** For a pull whose `target` is withheld, or whose row is authored on a withheld use's class (`cls/`, `sig/`,
`sup/`, `spc/` naming it), `row` is replaced by the family-level id `fam/<family>` and `says` by the family's plain
sentence (V11 §3.3.1), with `withheld: true`. `hardFails` entries pass the same replacement. A row of a concealed use the
key does not admit is dropped and not counted (rule (3)).
(4) **Goods.** `WhyLink.good` becomes optional and is absent whenever `other` is withheld.
(5) **Band-less reads.** Every read the clerk makes admits as at the city band, `inView` included: the session's view
supplies the bounding box only, never the band. State it in V10 §3.12 step 1 and in BCR-V10-1's *Knowledge* sentence.
(6) **Bars.** T-V10-6 gains canaries in class ids, signature-pair ids and goods ids of `local` and `secret` places, a
view at the building band, and a scan of every request body and transcript export for them. Eval group E gains "what
does the house behind the tannery sell?" at `public`.

**C10-02 — blocker — owner fidelity (item 109 (j) (2)). A player's clerk would learn of caves and ruins nobody in town
has found.** The owner: a cavern or ruin "exists whole whether or not anyone can reach it … the underground view draws it
in an unexcavated style … so a game master sees what the inhabitants do not; the clerk says so" (file g, item 109 (j)
(2)). The volume has no rule for it (0 hits for unexcavated, ruin, cavern). `MapBrief.layers.underground: boolean`
(l. 616) and the entity, gazetteer, `why` and `sites` reads admit underground elements by `knownTo` alone, so at `public`
a sealed ruin under the old quarter appears in the brief, can be read by address, and can be named in a reply.
*Required change:*
(1) **Absent below `secret`.** In V10 §3.12 and in BCR-V10-1's *Knowledge* text: an element of a cavern or ruin cluster
whose excavation reading is `unexcavated` (V04's derived `excavation(cluster)`, C4-48 (2)) is absent — not withheld — for
every key below `secret`. That covers every read, count, the brief, the delta lines of V10 §3.2, critique findings and
the grounding check's name index, exactly as for a concealed use (rule (3)): a withheld row would reveal that something
is there. This matches C4-56 (3) and V9C-04.
(2) **The brief's underground line** is computed after that filter (item (1) of C10-10 gives it its fields).
(3) **At `secret`** every answer about such an element carries `excavation: 'unexcavated'`, and the map block lists it
under "not yet found by anyone in town". The prompt gains a rule: "at a secret view, say which underground places are
unexcavated; never hint at them otherwise".
(4) **Bars.** T-V10-6 gains an unexcavated-ruin canary at `public` and `local`. Eval E gains "is there anything under the
town?" at `public` (the answer names nothing unexcavated) and at `secret` (it names the ruin as unexcavated).

**C10-03 — blocker — owner fidelity (items 20, 20 (h), 101 (d): "never invents a dossier fact"). The assistant's words
can state invented dossier facts and pass every check.** The structure keeps invented facts out of the map (V10 §3.13
"By structure"). The reply text is checked only for unknown names, mismatched link words, and "a sentence that names
SettlementForge or the dossier must link at least one `[dossier]` entity" (l. 1167). So "[[i12|the Silver Stag]] was
founded in 1203 and employs twelve guards" links a dossier entity, names SettlementForge nowhere, and passes. The same
holds for numbers about any place ("the tannery is 300 m from the river") that no tool returned.
*Required change:* extend `GroundingCheck.validate` with a **claims** step before the repair.
(1) **Attribute claims.** A sentence that links a `[dossier]`-tier entity and states an attribute of it is checked. An
attribute statement is detected as a number, a date, a year, a count word, or a quoted name that is not one of the
linked entity's admitted names. The value must equal (after the unit and rounding rules of V10 §3.3's map block) a
`facts` value of that entity returned by a read this segment. Otherwise the span is *unsupported*.
(2) **Numbers.** Every number in the reply that is next to a linked entity must match a value a tool result of this
segment returned for that entity or pair of entities, `measure` included (C10-22), within its rounding. Otherwise it is
*unverified*.
(3) **Rendering.** Unsupported and unverified spans are drawn as `unverified` blocks after the one repair, "not found on
the map" (V10 §5.4), never as fact. A dossier-tier chip is never attached to an unsupported span.
(4) **The prompt's rule 6** becomes "state a dossier fact only by quoting a `facts` row of tier `dossier` from a tool
result; state numbers only from tool results".
(5) **Bars.** T-V10-16 gains synthetic replies with an invented founding year, an invented count and an invented
distance, each flagged. Eval group F gains "tell me about the Silver Stag" on a dossier fixture whose record holds no
history: no unsupported span survives the repair on 100 % of runs.

## 3 Majors

### 3.1 Security, correctness and the owner's knowledge rules

**C10-04 — major — coherence, security posture, paid surface. A shared map file can change what the user's own key pays
for and write into the assistant's instructions.** `clerk.json` is "editable by `editTable`" with "a user's `editTable`
rows in the document's override layer" (l. 185, 446, 682, 1442). Its rows include `model.id`, `model.betas`, every
route's `effort`, `maxTokens` and `maxCalls`, `budgets.monthlyCapUsdDefault` and `turnCapUsd`, and `prices`. The system
prompt is "rendered with `clerk.json`'s lexicon and refusal rows" (V10 §3.3). A document's override layer travels with
the file, and a host may send tables as `editTable` events with provenance `host` (§11.4 door 3). So a map someone shares
can point the recipient's key at a dearer model, raise the per-turn call limit, or put arbitrary text into the trusted
system prompt through a lexicon word or a refusal template. Prompt rule 12 protects tool results, not the system prompt.
*Required change:*
(1) **Split `clerk.json` in two tables.** `clerk.ops` — `model`, `routes`, `cache`, `budgets`, `prices`, `retention` —
lives in the device's preference layer only (§7.6). A document or a host `editTable` on it is refused `invalid` with the
reason "assistant settings belong to this device". `clerk.content` — `lexicon`, `critique`, `refusals`, `brief`,
`spatial`, `encoders`, `variations`, `sizeBand`, `withheldWords` — stays document-overridable.
(2) **Document rows reach the prompt as data.** The lexicon and the refusal templates are rendered into the system prompt
only from the shipped and device layers. Document and host rows are appended to the first user message's map block as a
fenced "this map's own vocabulary" data block, each cell validated by schema: words of 1–40 letters, spaces and hyphens;
templates only from the shipped slot set.
(3) **Bar.** T-V10-21 gains a fixture document carrying `editTable` rows on every `clerk.ops` cell and an instruction in a
lexicon word: every `clerk.ops` row is refused, and the system prompt's bytes equal the shipped render.
(4) Record J-V10.38 and mark it owner-visible in V10 §11 as a security-posture choice (the owner may veto).

**C10-05 — major — correctness, determinism. The oracle cannot reproduce the placement score "to the last bit", because
places are chosen one after another.** V10 §3.9 step 5 (l. 1045) and J-V10.22 promise that `explain`'s score at a placed
plot equals the score S10b computed, re-scoring "the committed model". But S10b places items in order — claims first
(§7.1, §4.7), then item 105 (f)'s anchors-first order with a bounded relaxation pass. Coverage (103 (f)), competition and
same-kind spacing (107 (d)), and supply links to the nearest provider (105 (a)) all read the members already placed. At
explain time every later member is present too, so the terms differ. T-V10-9 would fail by construction on almost every
dispersed class, and `drifted` would light on untouched towns ("today the rules would put it elsewhere"), misinforming
the user.
*Required change:*
(1) **Placement-time context.** S10b records each placed item's order index `k` (and, for items the relaxation pass moved,
`pass: 2`) in its `DerivationRecord` (a BCR on §4.7 S10b). `explain` scores against the members of order below `k` (and
the relaxation pass's state for `pass: 2`), filtered from the committed placed set by index. That is deterministic, needs
no stored terms, and makes T-V10-9's equality hold.
(2) **Two readings.** `WhyAnswer` gains `mode: 'asPlaced'|'asNow'`. `asPlaced` is the default for `why`. `asNow` — the
full set, as today's text — is what `sites` and `drifted` use.
(3) **Drifted.** `drifted` is true only when an `asNow` candidate beats the plot's `asNow` score by more than a table
margin (`explain.driftMargin`, own, default 0.05 of the score range).
(4) **Fallback,** if the order index cannot be recorded at M3a: drop the bit-exact claim, state `asNow` only, and T-V10-9
becomes "the shares sum to 1 within 10⁻⁹ and the chance term equals its draw".

**C10-06 — major — correctness, lifecycle. A proposal that names what it just created names the wrong thing once the
map moves.** The `place` encoder follows `placeAt` with "`setAttr { id: the use it created … }` — the use's address from
the scratch's `ApplyResult.created`" (l. 1371). V10 §2.15 claims addresses are minted "on the scratch and again,
identically, on the user's document". That holds only when the user's `logHead` equals the scratch's `forkHead`. When it
moves — a hand edit, a host's dossier event, or bridged convergence (§4.2 step 4, "`doc.rejected { stale }` re-runs step
1") — the seqs shift. The staleness path then offers "show the new preview (the fresh dry run, accepted like any other)"
(l. 1119–1124), and that preview still carries the literal old address: the rename lands on another entity or fails.
The same holds for a `sites` variation and for `acceptLines`.
*Required change:*
(1) **Symbolic references.** Draft and proposal events store chained references as `{ created: { item: 'D<n>', event:
<index>, nth: <index into its created list> } }` placeholders, never a literal address.
(2) **Resolution.** They are resolved against `PreviewResult.created` (BCR-V10-6) at every preview, re-preview, accept and
bridged re-run, in item order.
(3) **Encoder rule.** A name on a new place goes into the creating event wherever the event kind carries one (`assign`
has `name`; the `quarter` sugar has `name`). The placeholder is needed only for `placeAt`.
(4) **Bar.** T-V10-14 gains a proposal whose `place` carries a name, an unrelated hand edit before Accept, and the check
that the name lands on the new use.

**C10-07 — major — wiring (V08 §4.4 (3); J-V10.20). SettlementForge's own assistant has no card in the map frame.**
V08 §4.4 (3) promises that "the module draws the ghost in the DM's frame with its one-line reason and variations … the
DM accepts in the frame". §11.3's `preview { events, view? }` carries no reason, no variations and no proposal id.
V10's `Proposal` and `ProposalView` are built only by the built-in harness's turn loop (V10 §3.11). In configuration C
nothing turns a bridged preview into a card, runs Accept, or tells the host what the DM chose.
*Required change:* V10 §3.17 gains **host proposal intake**, and BCR-V10-7 gains its messages.
(1) **The request.** `preview` gains `proposal?: { id: string; reason: string /* ≤ 140 */; variations?: { label: string;
events: EditEvent[] }[] /* ≤ 3 */ }`. With it, the module builds a `Proposal { source: 'host' }` and shows the same
`ProposalView` card (the AI mark included).
(2) **Accept** runs V10 §4.2 unchanged (`proposedBy: 'clerk'`, the DM as author) and sends `doc.changed`.
(3) **The answer.** A new PLAT → host message `clerk.proposal { id, status: 'accepted'|'dropped'|'stale'|'failed', seqs? }`
tells the assistant what happened.
(4) **Limits.** One waiting proposal per session (V10 J-V10.36 and V08 §4.4 (5) agree). A viewer's `preview` stays
refused.
(5) Record the wiring rows and T-V10-20's clauses.

**C10-08 — major — owner fidelity (J86 door 1), wiring. The words-only projection has no rows for the new question
kinds, and in configuration C the module itself sends their geometry to the host.** V10 §3.17 applies "V08 §5.4's
words-only projection" under configuration B. V08 §5.4 (3) defines the projection as "a fixed list of kept fields per
`Query` kind", and those rows exist only for the base's kinds. The new kinds `brief`, `entity`, `sites` and the new
`WhyAnswer` fields have none. Those fields include `MapBrief` bearings, `distM`, `areaHa` and `builtRadiusM`;
`EntityCard.anchor`, `bounds` and `groundCm`; `SiteCandidate.distM`; `WhyLink.distM`, `comfortM` and `maxM`; and
`closure` arcs by bearing. BCR-V10-1 says "a client that forwards answers to a model or a host strips them". In
configuration C, though, the module answers the host's bridged `query` itself: its `query.result` leaves the frame with
the geometry inside, before any client code strips it.
*Required change:*
(1) **Projection rows.** V10 §3.17 writes the rows for its kinds: for each of `MapBrief`, `EntityCard`, `SiteCandidate`
and `WhyAnswer`, the fields kept (names, kinds, addresses, districts, tiers, `facts` without numeric extents, `cause`,
pulls by family and `says`, `links` without distances, `members`, `history`) and the fields dropped (the rest).
(2) **Module-side projection.** A BCR on §11.3's `query.result`: in host mode the module applies the projection before
the reply leaves the frame, for these kinds and for `why`. V08 T-V8-27's fixture list gains the kinds, and T-V10-20
cites it.

**C10-09 — major — coherence (J-A101.83, §14). The volume contradicts three base sentences without a change request.**
(a) §11.2: "The tool API a clerk … drives is this API, **with nothing added for it**". BCR-V10-1, -5 and -6 add the
`brief`, `entity` and `sites` kinds, `scratch`, the `filtered` and `variations` options and `created`, all for the clerk.
(b) §14's clerk paragraph: "Its four roles are calls the API already has (§11.2)"; "it AUTHORS by sending declarations

description seed (§7.7 item 1)". BCR-V10-8 (c) changes only the tools-table row. J-V10.31 decides the clerk receives no
prose at all, and V08 §4.4 (4) repeats the seed.
*Required change:*
